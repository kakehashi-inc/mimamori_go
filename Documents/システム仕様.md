# システム仕様 - mimamori

各ホストで、指定した OS のユーザーの権限によって行われる操作を auditd の記録とファイルの走査で検知し、セントラルに集めて通知するシステムの設計書です。要件の定義はリポジトリ外の要件定義書、HTTP API の詳細は [API仕様.md](API仕様.md)、テーブルの詳細は [テーブル定義.md](テーブル定義.md) を参照してください。

## 1. 用語定義

| 用語（日本語） | English | 説明 |
| --- | --- | --- |
| セントラル | Central | 報告の受信と保存、通知、トークン、監視ルール、テンプレート、アカウントの管理、ブラウザ画面と管理用の API を提供する常駐プロセス。自ホストに対しては内蔵エージェントとしても機能する |
| エージェント | Agent | 監視対象の各ホストで動き、適用された監視ルールに従って検知し、セントラルに報告する常駐プロセス |
| 内蔵エージェント | Built-in agent | セントラルに含まれる、セントラル自身のホストを監視するエージェントの機能。通信とトークンを使わない。固定の識別名は `(central)` |
| 監視対象 | Monitored target | トークンで特定するエージェント 1 件、または内蔵エージェント。監視対象ごとに DB ファイルを持つ |
| 処理の流れ | Flow | アプリが作るスレッドやゴルーチンなど、並行して動く処理の単位 |
| ワーカー | Worker | セントラルでリクエストと定期的な処理を処理する処理の流れ |
| OS のユーザー | OS user | 監視の対象となる、各ホストの OS 上のユーザー |
| アカウント | Account | ブラウザ画面や CLI を使う利用者の登録情報。権限区分を 1 つ持つ |
| 管理者 | Administrator | 権限区分の 1 つ（`admin`）。すべての閲覧と操作ができる |
| 閲覧者 | Viewer | 権限区分の 1 つ（`viewer`）。閲覧だけができる |
| トークン | Token | セントラルがトークン名を付けて有効期限付きで発行する、エージェントの認証情報（`mmr_` で始まる） |
| CLI 用の秘密 | CLI secret | セントラルが起動のたびに作り、データディレクトリに置く値。CLI はこれで管理用の API に接続する。アカウントとは結び付かず、最大の権限を持つ |
| インスタンス ID | Instance ID | エージェントが初期化時に作り、ローカル DB（`agent.db`）に保存する値。トークンを 1 つのエージェントに結び付ける |
| 独自 CA | Private CA | セントラルが自動で作成し管理する認証局。エージェントおよび管理用の待ち受けのサーバー証明書に署名する |
| 繰り越し | CA rollover | 独自 CA の期限前に新しい独自 CA を作り、配布してから切り替える手順 |
| 監視ルール | Monitoring rule | エージェントに適用させる監視の内容（値だけ）。保存のたびに版が上がり、適用の操作でエージェントに届く |
| 版 | Version | 監視ルールを保存するたびに増える番号 |
| 適用 | Apply | 監視ルールの特定の版を、指定したエージェントに割り当てる操作 |
| テンプレート | Template | 監視ルールを作るための元。組み込みのテンプレート（Built-in template）と管理者のテンプレート（Administrator template）がある |
| 展開 | Expand | 1 つ以上のテンプレートをまとめて新しい監視ルールを作ること |
| 区分 | Category | 検知の重要度。`alert` または `normal` |
| 検知 | Detection | エージェントが監視ルールに従って見つけた事象 |
| 抑止条件 | Suppression | 管理者が正常と判断した検知の条件。一致した検知は記録だけ残し通知しない |
| 確認済み | Acknowledged | 管理者が内容を確認した検知 |
| 起点 | Scan base | ファイルの走査を始めるディレクトリ |
| 許可するパス | Allowed path | 書き込みを許すディレクトリ名の並び（例 `storage`、`bootstrap/cache`）。深さに関係なくパスの途中で一致を判定する |
| 正規に作られる場所 | Legitimate location | 実行されるファイルが正規に作られるディレクトリ名の並びと拡張子 |
| 未送信の報告 | Outbox | セントラルに送れなかった報告。エージェントのローカル DB に保存する |

## 2. 全体構成

```text
 monitored host                                   central host
+-----------------------------+                 +--------------------------------------------------+
| mimamori agent start        |   HTTPS (CA)    | mimamori central start                           |
|  (1 flow)                   | --------------> |  flow 1: accept + workers (default 1)            |
|  auditctl / ausearch        |  /agent/v1/*    |    :9081 HTTPS  /agent/v1/*  agents              |
|  file scan                  |                 |                 /admin/v1/*  CLI (loopback only) |
|  agent.db (SQLite)          |                 |    :9080 HTTP   /api/v1/*    browser (session)   |
|  data/                      |                 |                 /*           embedded SPA         |
+-----------------------------+                 |  flow 2: built-in agent (same code as the agent) |
                                                |  central.db  targets/agent-<id>.db  (SQLite)     |
 central host shell                             |  SMTP (company server) for notifications         |
+-----------------------------+   HTTPS (CA)    |                                                  |
| mimamori ctl ...            | --------------> |                                                  |
+-----------------------------+   127.0.0.1     +--------------------------------------------------+
```

- 1 つの実行ファイル `mimamori` がセントラル、エージェントの初期化と起動、CLI を提供します。
- 接続はエージェントからセントラルへの一方向のみです。セントラルからエージェントへは接続しません。
- パッケージ間の依存は `main -> workers -> modules -> models` の一方向です。`workers` が `init()` で `modules.StartCentral` にセントラルの起動関数を登録します（循環参照の回避）。

## 4. 処理の流れ

### 4.1 エージェント

- `agent start` は main の 1 つの流れだけで動きます。セントラルとの通信（`httpc.go`）、auditd のツールの実行（`runner.go`）、ファイルの走査、DB と設定の保存をすべてこの流れの中で順番に行います。
- 外部コマンドは `os.StartProcess` で起動し、標準出力と標準エラーをパイプで受け取ります（ファイルは作らない）。パイプは短い読み取りの期限付きで、`wait4(WNOHANG)` を短い間隔で確認する合間に読み出し、出力の上限を超えた分は読み捨てます。タイムアウトを過ぎたらプロセスグループごと `SIGKILL` します（`os/exec` のタイムアウトのようなゴルーチンを作らない）。
- 通信は 1 リクエスト 1 接続で、接続、TLS ハンドシェイク、送受信のすべてを接続の期限（30 秒）で打ち切ります。happy eyeballs の並列接続も無効にしています。
- 1 回の処理が確認の間隔より長くかかっても、次の処理はその終了後に始まります（間隔の残りが 1 秒未満なら 1 秒待つ）。
- 終了の指示（SIGINT / SIGTERM）は、処理の区切りと待機中に確認します。処理中は、その回の処理と状態の保存を終えてから終了します。
- Go ランタイムと標準ライブラリが内部で使う補助的なゴルーチン（GC、シグナルの受け渡し、`database/sql` の接続管理、名前解決）は、アプリの処理を並列化するものではないため対象外です。アプリの処理はすべて上記の 1 つの流れで行います。

### 4.2 セントラル

| 処理の流れ | 内容 |
| --- | --- |
| セントラルの機能（main） | 2 つの待ち受けを交互に短い期限付きで `Accept` し、受け付けた接続と定期的な処理（30 秒ごと）を待ち行列に入れる。ワーカー数が 1（既定）のときは、この流れ自身が待ち行列を 1 件ずつ処理する |
| ワーカー（ワーカー数が 2 以上のとき） | ワーカー数と同じ数のゴルーチンが待ち行列の仕事を処理する。main は受け付けと振り分けだけを行う |
| 内蔵エージェント | エージェントと同じ `AgentRuntime` を 1 つのゴルーチンで動かす |

- 接続ごとのゴルーチンを作る `net/http.Server` は使いません。受け付けた接続 1 つにつき 1 リクエストを `http.ReadRequest` で読み、`http.Handler` を呼び、応答を `Connection: close` で書きます。
- 待ち行列の接続は、設定の時間（既定 10 秒）以内に処理できなければ拒否します（HTTP は 503、HTTPS は切断）。待ち行列の上限は 256 です。
- ワーカー数が 1 のときは、処理中に届いた接続はカーネルの待ち行列で待つため、受け付けた時刻ではなく前回の受け付けの確認の時刻から待ち時間を数えます。遅い要求の処理で待たされた接続も、設定の時間を超えれば拒否します。
- 1 リクエストはヘッダーの読み取りと TLS ハンドシェイクを 10 秒、全体を 60 秒で打ち切ります。要求の本文は 32 MiB までです。
- 定期的な処理も待ち行列の仕事として扱うため、ワーカー数の範囲内で動きます。同時に 2 つは動きません。
- SMTP との通信は接続の期限（既定 30 秒）で打ち切ります。

### 4.3 起動と終了

- エージェントの起動前の確認: auditd のツール（`auditctl`、`ausearch`）が使える、`auditctl -s` で auditd が動いていて有効（`pid` が 0 でない）、データディレクトリの所有者が実行ユーザーで group と other の権限が無い、`agent.db` に設定（接続先、トークン、独自 CA、インスタンス ID）がそろっている。満たさなければ起動しません。
- 実行ユーザーを root に限定する確認は行いません。必要な権限（auditd の操作、`/etc/audit/rules.d` への書き込み、監査ログの読み取り、データディレクトリの読み書き、プロセスへのシグナル）は、それぞれの操作の結果で判断し、足りなければその操作のエラーとして報告します。なお、`auditctl` は多くのディストリビューションで root 以外の実行を拒否するため、エージェントと内蔵エージェントは実質的に root での実行になります。セントラルの機能、`status`、`stop`、`init-admin`、`reset-password`、`ctl` は、データディレクトリなどへの権限があれば root 以外でも動作します。
- 多重起動は、データディレクトリのロックファイル（`agent.lock` / `central.lock`）への `flock(LOCK_EX|LOCK_NB)` で防ぎます。起動したプロセスはロックファイルに自分のプロセス ID を書きます。
- 常駐は supervisor などから行い、終了は SIGTERM（または SIGINT）で指示します。手動で運用する場合は `central stop` / `agent stop` が同じく SIGTERM を送り、プロセスが処理の区切りで終了してロックを解放するまで待ちます（既定の待ち時間はセントラル 120 秒、エージェント 300 秒、`--timeout` で変更。待ち時間を過ぎると終了コード 7）。起動していなければその旨を表示して終了コード 0 です。
- `central status` / `agent status` は、ロックファイルを保持しているプロセスの有無で稼働中かを判定し、プロセス ID と起動時刻を表示します。エージェントは接続先、トークン名と有効期限、適用中の監視ルール、最後の適用の結果、未送信の報告の件数も表示します。停止中は終了コード 3 を返します。ロックファイルは読むだけで変更しません。
- セントラルは起動時に auditd を確認し、使えない場合もセントラルの機能は起動して内蔵エージェントだけを停止状態にします。理由はログと、画面の上部の警告（`GET /overview`）に表示します。
- エージェントは起動時に、保存している監視ルールを適用し直します（再起動や auditd の再起動で OS 標準のルールが読み込み直されるため）。

## 5. CLI

`mimamori [--data-dir DIR] <command>`

| コマンド | 説明 |
| --- | --- |
| `central start` | セントラルを起動する |
| `central stop [--timeout DURATION]` | 起動中のセントラルを停止する（SIGTERM を送り、停止するまで待つ） |
| `central status` | セントラルが稼働中かを表示する（停止中は終了コード 3） |
| `central init-admin --name NAME [--language auto\|en\|ja]` | 管理者が 1 人もいない場合に限り、最初の管理者を作成する（セントラルのデータディレクトリにアクセスできるユーザーで実行。表示言語の既定は auto、パスワードは端末から入力、または標準入力の 1 行目） |
| `central reset-password --name NAME` | 管理者のパスワードを再設定する（セントラルのデータディレクトリにアクセスできるユーザーで実行）。アカウントを有効にし、セッションを無効にする |
| `central config list` / `get NAME` / `set NAME [VALUE]` / `unset NAME` | セントラル管理用 DB に保存した設定の一覧、表示、変更、既定値への戻し（6 章）。DB を直接読み書きするため、セントラルの停止中も使える。動いているセントラルは 30 秒ごとに設定を読み直して反映する（再起動後に反映する項目を除く） |
| `agent init --server URL [--overwrite] [--ca-fingerprint FP]` | エージェントを初期化する。トークンは端末から（エコー無し）または標準入力の 1 行目から読む |
| `agent start` | エージェントを起動する |
| `agent stop [--timeout DURATION]` | 起動中のエージェントを停止する（SIGTERM を送り、その回の処理を終えて停止するまで待つ） |
| `agent status` | エージェントが稼働中かと状態を表示する（停止中は終了コード 3） |
| `ctl [--json] <group> <command>` | 管理用の API を使う管理コマンド（下表） |
| `version` | バージョンを表示する |

`ctl` のコマンド:

| グループ | コマンド |
| --- | --- |
| `agents` | `list`、`show ID` |
| `tokens` | `issue NAME [--valid-days N] [--rule ID] [--rule-version V]`、`list`（トークンの値を含め、省略せずに表示）、`show ID`、`reissue ID [--valid-days N]`、`unbind ID`、`revoke ID` |
| `rules` | `list`、`show ID [--version V]`、`create NAME [--template T]... [--choice FIELD=TEMPLATE]... [--file F] [--description D]`、`export ID [--version V]`、`save ID --file F [--comment C] [--description D]`、`edit ID [--comment C] [--editor CMD]`（エディタ（既定 `vi`）で編集して保存）、`history ID`、`diff ID FROM TO`、`apply ID --agent ID... [--version V]`、`to-template ID NAME [--version V]`、`delete ID` |
| `templates` | `list`、`show NAME`、`create NAME [--from-builtin T \| --from-rule ID --version V \| --file F]`、`update NAME --file F`、`delete NAME` |
| `detections` | `list [--agent ID] [--category C] [--type T] [--from T] [--to T] [--acknowledged true\|false] [--suppressed true\|false] [--limit N] [--offset N]`、`show AGENT_ID ID`、`ack AGENT_ID:ID...` |
| `suppressions` | `list`、`create [--agent ID] [--type T] [--user U] [--exe E] [--target T] [--comment C]`、`delete ID` |
| `accounts` | `list`、`create NAME --role R [--language auto\|en\|ja]`、`role ID R`、`password ID`、`disable ID`、`enable ID`、`delete ID` |
| `certs` | `status` |
| `history` | `[--category C] [--limit N] [--offset N]` |

- `ctl` は設定を持ちません。管理用の API はセントラル自身の待ち受けなので、接続先はセントラル管理用 DB の設定 `agent_listen` のポートと `127.0.0.1` から、CA 証明書はデータディレクトリの `ca.crt` から決めます。`agent_listen` を変更してセントラルを再起動するまでの間は、CLI は新しいポートに接続するため使えません（画面に「再起動待ち」と表示される）。
- CLI はアカウントと結び付かず、最大の権限を持ちます。セントラルは起動のたびに新しい CLI 用の秘密を作ってデータディレクトリの `cli.secret`（0600）に書き、CLI はそれを読んで管理用の API に接続します。CLI を使えるのは、そのファイルを読める OS ユーザーだけです。入力や設定は要りません。履歴の操作者は `cli` と記録します。
- このアプリ独自の環境変数はありません（設定は DB に保存し、コマンドと引数で行います）。外部コマンド（`auditctl`、`ausearch`、`ctl rules edit` のエディタ）は `PATH` から探して起動し、このプロセスの環境を引き継ぎます。出力を解析する `auditctl` と `ausearch` だけは、出力の形式と時刻の解釈が利用者の設定に左右されないよう、`LC_ALL=C`、`TZ=UTC` に置き換えて起動します。表示の時刻は通常のローカル時刻（`TZ`、無ければ `/etc/localtime`）です。
- 実行ファイルの場所は起動時のパス（`argv[0]`）から求めるため、絶対パスか `./mimamori` のようにパスを付けて起動します（名前だけで起動するとエラー）。
- 接続先はループバックアドレスに限ります。サーバー証明書は独自 CA で検証します。
- 終了コード: 0 正常、1 一般エラー、2 引数エラー、3 設定エラー、4 認証エラー、5 実行エラー、6 ファイル I/O エラー、7 タイムアウト。

## 6. 設定と保存場所

設定ファイルはありません。設定もデータも、データディレクトリ（既定は実行ファイルと同じディレクトリの `data/`、`--data-dir` で変更）の SQLite に保存します。このアプリが作成、更新、削除するファイルは、データディレクトリの中と auditd のルールファイル（`/etc/audit/rules.d/zz-mimamori.rules`）だけです（外部コマンドの出力はパイプで受け取り、SQLite の一時データはメモリに置き、CLI の編集用の一時ファイルは `data/` に作る）。それ以外は、監視と自ホストの情報のために読むだけです（`/etc/passwd`、`/etc/group`、`/etc/os-release`、`/etc/audit/auditd.conf`、監査ログ、監視ルールで指定した走査の対象）。`data/` はシンボリックリンクにして別の場所に置けます（リンク先を使い、リンク先の権限は変更しない）。セントラルとエージェントのデータファイルは名前が重ならないため、同じ `data/` を使えます。実行ファイルのディレクトリ自体の所有者と権限は変更も確認もしません。

| ファイル | 内容 |
| --- | --- |
| `central.db` | セントラル管理用 DB。設定（`settings` の `config.<項目>`）、アカウント、監視ルール、トークン、証明書など |
| `targets/agent-<id>.db` | 監視対象ごとの検知と自ホストの情報 |
| `builtin-agent.db` | 内蔵エージェントのローカル DB |
| `agent.db` | エージェントのローカル DB。設定（`state` の `config.<項目>`: 接続先、トークン、信頼する独自 CA、トークン名と有効期限、インスタンス ID）と動作の状態 |
| `ca.crt` | CLI が使う独自 CA の公開の証明書（0644） |
| `cli.secret` | CLI 用の秘密（0600、セントラルの起動のたびに作り直す） |
| `central.lock`、`agent.lock` | 多重起動の防止と、`stop` / `status` で動いているプロセスを見つけるため |

データディレクトリは無ければ 0700 で作ります。既存の場合は変更せず、実行ユーザーの所有で他のユーザーが読み書きできないことを確認します（SMTP のパスワードやトークンを含むため）。

セントラルの設定は、管理者がブラウザの「システム設定」画面（`/config`）または `central config` で変更します。保存していない項目は既定値です。値の組み合わせは保存時に検証し、不正な値は保存しません。変更は履歴（`config`）に残し、`smtp.password` の値は残しません。

- 再起動後に反映: `web_listen`、`agent_listen`、`workers`、`queue_timeout_sec`、`builtin_agent`。動いているセントラルは起動時の値を使い続け、画面では保存した値と使っている値が異なる項目を「再起動待ち」と表示します。
- 即時反映: それ以外の項目。画面での変更は保存した時点で、`central config` での変更はセントラルが 30 秒ごとに設定を読み直した時点で反映します。`server_names` を変えると、次の確認でサーバー証明書を発行し直します。

| 項目 | 既定値 | 説明 |
| --- | --- | --- |
| `web_listen` | `0.0.0.0:9080` | ブラウザ用の待ち受け（HTTP）。アドレスは IP アドレスで指定する（待ち受けはシステムコールで作り、`/proc` を読まないため名前解決もしない） |
| `agent_listen` | `0.0.0.0:9081` | エージェントおよび管理用の待ち受け（HTTPS）。IP アドレスで指定する |
| `server_names` | なし | サーバー証明書に含めるホスト名と IP アドレス（カンマ区切り）。`127.0.0.1`、`::1`、`localhost` は常に含める |
| `workers` | 1 | リクエストを処理するワーカーの最大数（64 まで） |
| `queue_timeout_sec` | 10 | 待たせた接続を拒否するまでの時間 |
| `token_valid_days` | 365 | トークンの有効期間の既定値 |
| `token_renew_before_days` | 30 | 残りの有効期間がこれを下回ったら自動更新する |
| `retention_days` | 180 | 検知の保存期間 |
| `default_check_interval_sec` | 60 | 監視ルールが無いエージェントの確認の間隔 |
| `session_hours` | 12 | ブラウザのセッションの有効時間（操作のたびに延長） |
| `session_remember_days` | 30 | 「ログインを保持する」を選んだ場合のセッションの有効期間（ログインから。365 まで） |
| `builtin_agent` | true | 内蔵エージェントを使うか |
| `notify.min_interval_min` | 30 | 通知の最小間隔（全体で 1 通） |
| `notify.dedupe_hours` | 24 | 同じエージェントの同じ検知を再送しない期間 |
| `notify.max_lines` | 200 | 本文の行数の上限 |
| `notify.subject_prefix` | `[mimamori]` | 件名の接頭辞 |
| `smtp.host` / `smtp.port` | なし / 587 | SMTP サーバー（`smtp.security` により 587 / 465 / 25） |
| `smtp.security` | `starttls` | `starttls` / `tls`（接続時から）/ `none` |
| `smtp.auth`、`smtp.username`、`smtp.password` | false | 認証の有無と認証情報（PLAIN、暗号化無しでは LOGIN）。`smtp.password` は引数では受け取らず、端末（エコー無し）または標準入力から読む。一覧では値を表示しない |
| `smtp.from`、`smtp.to` | なし | 送信元と宛先（カンマ区切り）。`smtp.host`、`smtp.from`、`smtp.to` がそろったときだけ通知する |
| `smtp.timeout_sec`、`smtp.helo_name` | 30、なし | タイムアウトと HELO 名 |

プログラムは起動時に umask を 077 にし、作成するファイルとディレクトリを実行ユーザー以外が読み書きできないようにします。既存のディレクトリの所有者は変更せず、実行ユーザーと異なる場合はエラーにします。

### 6.0 セントラルの移設

- 設定とデータはすべてデータディレクトリにあり、DB には絶対パスを保存しません（監視対象ごとの DB は `agents.db_file` にファイル名だけを保存し、データディレクトリからの相対で開く）。実行ファイルの場所は起動時に求めます。このため、停止したセントラルのディレクトリを所有者と権限を保ったまま移せば、別のパスや別のホストでもそのまま動作します（SQLite の `-wal` / `-shm` も含めて移すか、停止後に移す）。
- 起動時に作るもの（`cli.secret`、`ca.crt`、ロックのファイル）は作り直します。独自 CA、サーバー証明書、トークン、セッションは DB にあるため、エージェントとブラウザのログインはそのまま使えます。
- エージェントは初期化時の URL に接続するため、URL のホスト名を新しいホストに向けます（証明書の名前は `server_names`）。IP アドレスの URL で初期化したエージェントは、アドレスが変わる場合、トークンの再発行と `agent init --overwrite` が必要です。
- 内蔵エージェントは起動時に監視ルールを新しいホストの auditd に適用し直します。元のホストの `/etc/audit/rules.d/zz-mimamori.rules` は残るため、元のホストを使い続ける場合は削除します。

### 6.1 データベースとマイグレーション

- セントラル管理用（`central.db`）、監視対象ごと（`targets/agent-<id>.db`）、エージェントのローカル（`agent.db` / `builtin-agent.db`）の 3 種類の SQLite ファイルは、それぞれ `app/migrations/central`、`agentdb`、`agentlocal` のマイグレーションを持ち、各ファイルの `goose_db_version` に適用済みの版を記録します。
- DB を開くときに未適用のマイグレーションを順に適用します。セントラルは起動時にすべての監視対象の DB を開くため、新しい版のプログラムで起動すると、既存のすべての DB ファイルが更新されます。

### 6.2 時刻

- DB には時刻を Unix 秒（UTC）で保存します。API は RFC3339 の UTC で返します。
- 表示はローカル時間です。ブラウザ画面はブラウザのタイムゾーン、CLI（`ctl`）と通知メールとエージェントのログはそのホストのタイムゾーンで表示します。履歴の詳細の文中に含まれる日時も表示時にローカル時間に変換します。CLI の `--json` の出力は API の値（UTC）のままです。

## 7. 監視ルール

### 7.1 内容

監視ルールは値だけを持ち（`modules.RuleContent`）、auditd のルールの文字列や auditd 全体の設定は含められません。未知の項目は拒否します。

| 項目 | 説明 |
| --- | --- |
| `users[]` | OS のユーザー（`value`、`if_missing`: `ignore` / `warn`） |
| `exclude_interactive` | true（既定）でログインした利用者の操作と cron のジョブを対象外にする（`auid` が未設定のプロセスだけを対象にする） |
| `check_interval_sec`、`scan_interval_sec` | 確認の間隔（10-3600、既定 60）、書き込み可能な状態の走査の間隔（60-604800、既定 3600） |
| `exec.category`、`denied.category` | 実行、拒否された操作の区分 |
| `read.dirs[]`、`read.category` | 読み込みを監視するディレクトリ（要素）と区分 |
| `network.executables[]`、`network.category` | 通信を監視する実行ファイル（要素）と区分 |
| `writable.base`、`writable.allowed_paths[]`、`writable.category` | 走査の起点、許可するパス、区分 |
| `exec_files.extensions[]`、`exec_files.legit[]`、`exec_files.other_category` | 拡張子、正規に作られる場所（`path`、`extensions`、`category`）、それ以外の区分 |

種類ごとに、必要な項目がそろったときだけ監視します（[API仕様.md](API仕様.md) の 6 章）。区分の空文字は「指定なし」です。

検証（保存時、テンプレートの保存時、エージェントでの適用前）: パスは絶対パスで `.`、`..`、空白、引用符を含まない、許可するパスと正規に作られる場所はディレクトリ名の並び、拡張子は `.` と英数字 1-15 文字、OS のユーザー名の形式、各一覧は 200 件（拡張子は 50 件）まで、間隔は範囲内、区分は `alert` / `normal`。

### 7.2 テンプレートの展開

- 一覧の項目（OS のユーザー、ディレクトリ、実行ファイル、許可するパス、拡張子、正規に作られる場所）は、テンプレートの順に合わせて重複を除きます。同じ要素で `if_missing` が異なる場合は `warn` を採用します。
- 単一の値の項目が複数のテンプレートで異なる場合は衝突とし、`POST /rules/merge-preview` が候補を返します。管理者が `choices`（項目ごとに採用するテンプレート名）を指定して作成します。正規に作られる場所は、パスと拡張子が同じで区分が異なる場合に衝突とします。
- 展開した内容は新しい監視ルールの版 1 としてコピーするため、テンプレートを後で変更しても監視ルールは変わりません。

### 7.3 保存と適用

- 保存（`PUT /rules/{id}`）のたびに `rule_versions` に新しい版を追加します。エージェントには届きません。
- 適用（`POST /rules/{id}/apply`）は `agents.assigned_rule_id / assigned_rule_version` を更新します。同期の応答には割り当て中の版を毎回含め、エージェントは動作中の版と異なる場合だけ適用します。
- エージェントの一覧と詳細では、適用した版、エージェントが適用を報告した版、保存済みの最新の版を表示し、適用した版と最新の版が異なれば「最新でない」と示します。
- いずれかのエージェントに適用されている監視ルールは削除できません（409、外部キーでも保護）。

## 8. エージェントとセントラルの通信

### 8.1 初期化（agent init）

1. auditd が存在して動いており、`auditctl`、`ausearch` が使える
2. 初期化済み（`agent.db` に設定がある）の場合は `--overwrite` がある
3. トークンを端末（エコー無し）または標準入力から読む（引数や環境変数では受け取らない）
4. `GET /agent/v1/ca` を証明書の検証無しで呼んで独自 CA を受け取り（`--ca-fingerprint` を指定した場合は一致を確認）、以後はその独自 CA だけを信頼して `POST /agent/v1/sync` でトークンとインスタンス ID を送って認証する（初回ならトークンがインスタンス ID に結び付く。インスタンス ID は初回の初期化で作り、再初期化では `agent.db` にあるものを使い続ける）
5. データディレクトリ（実行ユーザー所有の 0700）と `agent.db` を作り、設定を 1 つのトランザクションで保存する

途中で失敗した場合、データディレクトリと `agent.db` は作らず（再初期化では既存の設定を変更せず）、この実行で作ったものは削除します。成功したら、auditd.conf にホストを停止させる設定（`space_left_action`、`admin_space_left_action`、`disk_full_action`、`disk_error_action` が `halt` / `single`）があれば警告し、トークン名、有効期限、適用されている監視ルール（無ければその旨）、独自 CA のフィンガープリントを表示します。

### 8.2 定期的な処理

1. `POST /agent/v1/sync`: 適用中の監視ルールと版、信頼している独自 CA、最後の適用の結果を送る。応答の監視ルールの版が変わっていれば適用する。応答に新しいトークンや独自 CA があれば `agent.db` に保存する
2. auditd の記録から前回の続きの検知を取得する（監視ルールに auditd を使う種類がある場合）
3. ファイルを走査する（書き込み可能な状態の走査はその間隔ごと）
4. 検知、自ホストの情報、適用の結果をまとめて未送信の報告に入れ、古い順に `POST /agent/v1/report` で送る

- 監視ルールが無いエージェントは監視を行わず、自ホストの情報だけを報告します。走査の起点の既定値は無く、ディレクトリの構成は適用中の監視ルールに走査の起点がある場合だけ報告します。
- 接続できない間は、最後に適用した監視ルールで監視を続け、報告をローカル DB に保存して次回にまとめて送ります。保存する検知は 10,000 件までで、超えたら `normal` の検知から古い順に捨て（それでも超える場合は `alert` を古い順に）、捨てた件数を次の報告で送ります。セントラルは累計を表示し、履歴に残します。
- 接続できないままトークンの期限が近い場合、トークンを拒否された場合（期限切れ、失効、再発行、インスタンス ID の不一致）、証明書を検証できない場合（繰り越しに間に合わなかった）は、エージェント自身のログ（標準エラー）に出力します。

### 8.3 認証と拒否

- 認証付きの要求は `Authorization: Bearer mmr_...` と `X-Mimamori-Instance-Id` を送ります。
- トークンが無い、無効、期限切れ、失効、インスタンス ID が無い、または一致しない場合は、理由を返さずに 401 とし、履歴（`rejected`）に接続元と理由を残します。同じ接続元、理由、トークン名の拒否は 10 分以内なら 1 行の回数にまとめます。

### 8.4 トークンの自動更新

- 同期の時点で残りの有効期間が `token_renew_before_days` を下回っていれば、`renew_counter` を増やし、新しい値を `HMAC-SHA256(server_key, "token-renewal:<id>:<counter>")` から導出して、そのハッシュを `pending_hash` に保存し、値を応答に含めます。
- 値を導出で作るため、未使用の新しい値はハッシュだけを保存しつつ、エージェントが保存に失敗した場合に次の接続で同じ値を再び渡せます。
- 新しい値で最初に接続した時点で `hash` と `value` を置き換え、古い値を無効にします。それまでは古い値もその有効期限まで受け付けます。
- エージェントは新しい値を `agent.db` に 1 つのトランザクションで保存します。失敗したら古い値で接続を続けます。
- トークン名、インスタンス ID の結び付け、検知、適用中の監視ルールは agents 行と監視対象ごとの DB に結び付いているため、更新の前後で変わりません。

### 8.5 再発行と失効

- 再発行は新しい乱数の値と有効期限を設定し、`pending_hash` を消すため、それまでの値はすべて無効になります。失効も解除します。インスタンス ID の結び付けは維持します（別のエージェントにする場合は結び付けを解除する）。
- 失効は `revoked_at` を設定し、以後の接続を拒否します。

## 9. auditd の扱い

### 9.1 生成するルール

監視ルールの値を次のひな形に当てはめて生成します。すべてのルールにキー `mimamori` を付けます。`exclude_interactive` が有効なら各ルールに `-F auid=4294967295` を加えます。

| 種類 | ルール（ユーザーごと / 要素ごと） |
| --- | --- |
| 実行 | `-a always,exit -F arch=b64 -S execve -F euid=<uid> -k mimamori`（b32 も） |
| 拒否された操作 | `-a always,exit -F arch=b64 -S <ファイル操作の syscall> -F exit=-EACCES -F euid=<uid> -k mimamori`（`-EPERM` も） |
| 読み込み | `-a always,exit -F arch=b64 -F dir=<dir> -F perm=r -F success=1 -F euid=<uid> -k mimamori` |
| 通信 | `-a always,exit -F arch=b64 -S connect -F exe=<path> -k mimamori` |

全体の設定: `-b 8192`、`-f 1`（障害時にホストを停止させない）、`--backlog_wait_time 0`（記録が溢れてもプロセスを待たせない）。

### 9.2 適用の手順

1. 監視ルールを検証する。失敗したら適用せず、前の監視ルールのまま動作してエラーを報告する。適用に失敗した版は確認のたびに再試行しない（再試行のたびに読み込み済みのルールを入れ替えて監視が途切れるため）。管理者が別の版を適用するか、エージェントを再起動すると再び適用する。動作中の版が改めて割り当てられた場合は、その版の成功した適用の結果を報告し直す
2. OS のユーザー、ディレクトリ、実行ファイルの存在を確認する。存在しない要素は除外し、`warn` の要素は警告として報告する
3. ルールを生成する
4. `auditctl -s` で `enabled 2`（変更不可）なら失敗とする
5. 永続化のため `/etc/audit/rules.d/zz-mimamori.rules` に全体の設定と生成したルールを書く（OS 標準のファイルは編集しない。augenrules は rules.d を C ロケールのファイル名の順に連結し、全体の設定は後の値が有効になる。番号の無い OS 標準のファイル（Ubuntu の `audit.rules` など）よりも後に並ぶよう `zz-` で始まる名前にして、OS 標準の値を上書きする）
6. 読み込まれているルールのうち、キー `mimamori` のものだけを 1 件ずつ `auditctl -d` で削除する（他のルールに影響しない）
7. 全体の設定を `auditctl` で設定する
8. `-a never,task`（Amazon Linux 2023 などで、すべてのシステムコールの監査を抑制する既定のルール）が読み込まれていれば `auditctl -d never,task` で打ち消し、その時刻を記録する
9. 生成したルールを読み込む
10. `auditctl -l` で件数と抑制ルールの無いこと、`auditctl -s` で `failure 1` と `backlog_wait_time 0` を確認する。いずれかの段階で失敗したら、キー `mimamori` のルール、全体の設定、ルールファイルを元に戻してエラーを報告する

打ち消す前から動いているプロセスには監査が効かないため、導入の案内で、打ち消した後に監視対象のユーザーで動いているプロセスを再起動するよう案内します（プロセスの一覧は `/proc` を読まないため取得しません）。自ホストの情報では、抑制ルールが残っているかを報告します。

### 9.3 記録の取得と集約

- 前回の続きの読み取りは、エージェントが最後に読んだイベントの位置（時刻の秒とミリ秒、通し番号）をローカル DB に保存して行います。`ausearch --input-logs --raw -k mimamori -ts <最後のイベントの秒>` で読み、すでに読んだイベントを除きます。`--input-logs` はローテーションした記録も読みます。初回は 10 分前から読みます。ausearch のチェックポイント機能は、版によって新しいイベントを返さないことがあるため使いません。
- ausearch は `LC_ALL=C`、`TZ=UTC` で実行し、`-ts` の日付は C ロケールの形式（`MM/DD/YY`）で渡します。日付の誤りなどで終了コード 1 と標準エラーにエラーを返した場合は、読み取りの失敗として扱います。
- SYSCALL、EXECVE、PATH、CWD、SOCKADDR の記録をイベントごとにまとめ、次の規則で種類を判定します: 成功した execve / execveat は実行、権限で拒否された（`-EACCES` / `-EPERM`）execve は拒否された操作、それ以外の失敗した execve（PATH の探索で見つからないなど）は除外、connect は通信（IPv4 / IPv6 の相手のみ。UNIX ソケットは除外）、失敗で `-EACCES` / `-EPERM` は拒否された操作、成功のそれ以外は読み込み。
- 「種類、OS のユーザー（euid の名前）、実行ファイル、対象（実行はコマンドライン、ファイルは CWD を考慮した絶対パス、通信は IP:ポート）」の組ごとに件数と最初と最後の発生時刻にまとめます。

## 10. ファイルの走査

- シンボリックリンクはたどらず（`WalkDir` と `Lstat`）、起点と異なるファイルシステムのディレクトリには入りません。1 回の走査は 2,000,000 項目までです。
- 許可するパスと正規に作られる場所は、起点からの相対パスの途中の連続したディレクトリ名として判定します（`storage` は `/opt/a/storage`、`/opt/a/prod/storage`、`/opt/x/a/prod/storage` のいずれにも一致）。
- 書き込み可能な状態（`scan_interval_sec` ごと）: 許可するパスに一致するディレクトリは記録して中に入らず、それ以外で、監視ルールの OS のユーザーが所有する、またはグループかその他に書き込み権限があるファイルとディレクトリを検知します。報告済みの（パス、状態の変更時刻、所有者、権限）の組は再報告しません。
- 実行されるファイル（毎回）: 最後の全体の走査で見つけた許可するパスのディレクトリだけをたどり、指定した拡張子で、状態の変更時刻（ctime。所有者が偽装できる更新時刻は使わない）が前回の確認より新しいファイルを検知します。正規に作られる場所の中で拡張子も一致すればその区分、それ以外は `other_category` です。初回の走査では、既存のファイルのうち正規に作られる場所のものは報告しません。

## 11. 自ホストの情報

OS の名前とバージョン（`/etc/os-release`）、ホスト名、カーネル（`uname` システムコール）、auditd の状態（`auditctl -s` の値、取りこぼしの件数、抑制ルールの有無、ホストを停止させる設定）、適用中の監視ルールの走査の起点の配下 3 階層までのディレクトリ（300 件まで）、エージェントのバージョン、適用中の監視ルールと版、最後の適用の結果、信頼している独自 CA。`/proc` と `/etc/machine-id` は読みません。そのため、要件にある「動いている Web サーバーと php-fpm のプロセスと実行ユーザー」と「抑制ルールの影響を受けているプロセス」は報告しません。セントラルはディレクトリの構成から監視ルールへの追加の候補（`storage` / `bootstrap/cache` / `uploads` など、まだ許可するパスに無いディレクトリ）を作ります。

なお、`/proc` は mimamori のコードからは読みませんが、Go の実行環境（`/proc/self/cgroup`、`/proc/self/mountinfo`）、SQLite ドライバー（`/proc/self/exe`、`/proc/self/maps`）、`auditctl` などの auditd の道具は、それぞれ自身の処理で読みます。

## 12. セントラルの機能

### 12.1 検知の保存

- 報告の検知は、その監視対象の DB に保存します。同じ fingerprint の未確認の行があれば件数と時刻をまとめ、無ければ新しい行を作ります。確認済みにした後の発生は新しい行になります。
- 抑止条件に一致した検知は `suppressed = 1` で記録し、通知しません。抑止条件を作成した時点で、一致する未確認の検知にも反映します。
- 保存期間（既定 180 日）を過ぎた検知は 1 時間ごとに削除します。拒否した接続の履歴も同じ期間で削除します。

### 12.2 通知

- 30 秒ごとの定期的な処理で、前回の作成から最小間隔（既定 30 分）を過ぎていて、通知待ちの検知があればメールを 1 通作成します。最小間隔の間に増えた検知は次の 1 通にまとめます。
- 新しい検知は通知待ちになります。同じ fingerprint を設定の期間（既定 24 時間）以内に通知していれば通知しません。期間を過ぎて同じ検知が再び発生したら通知します。
- 件名: `alert` を含む場合は `[mimamori] [ALERT] N alert(s), M new detection(s)`、含まない場合は `[mimamori] M new detection(s)`。
- 本文: エージェント（トークン名、または `(central)`）とホスト名ごとに、`alert`、`normal` の順（同じ区分の中は新しい順）で 1 検知 1 行（区分、種類、ユーザー、実行ファイル、対象、権限、件数、最後の時刻）。上限（既定 200 行）を超えた分は件数だけを示します。
- 作成したメールは `notifications` に保存し、送信できるまで定期的な処理のたびに再送します。

### 12.3 独自 CA とサーバー証明書

- 初回起動時に独自 CA（ECDSA P-256、5 年）とサーバー証明書（397 日、`server_names` とループバック）を作成します。
- サーバー証明書は、残り 30 日を下回った、名前の設定が変わった、署名した CA が現在の CA でない場合に作り直し、再起動せずに切り替えます（`GetCertificate`）。
- 繰り越し: 独自 CA の残りが 180 日を下回ったら新しい CA（`next`）を作ります。同期の応答で、エージェントが持っていない CA を配布します。エージェントは新旧の両方を信頼します。30 日後に新しい CA を `active` にし、古い CA を `retired`（期限まで信頼）にして、新しい CA で署名したサーバー証明書に切り替えます。期限切れの CA は破棄します。
- 新しい CA をまだ受け取っていないエージェント（同期で送られたフィンガープリントに現在の CA が無い）を画面に表示します。繰り越しに間に合わなかったエージェントは初期化し直して復旧します。
- 証明書と秘密鍵は central.db（0600）に保存します。CLI 用に公開の CA 証明書を `ca.crt` に書きます。

### 12.4 アカウントと認証

- パスワードは PBKDF2-SHA256（600,000 回、16 バイトの salt）で保存します。10 文字以上です。
- ログインに 5 回続けて失敗すると、そのアカウントは 15 分間ログインできません。存在しないアカウント名でも同じ時間がかかるように、ダミーのハッシュを検証します。
- セッションは Cookie `mimamori_session`（HttpOnly、SameSite=Strict）で、値のハッシュだけを保存します。ブラウザに保存するのはこの Cookie だけです（localStorage などは使わない）。
- 通常のセッションは有効期限の無い Cookie（ブラウザを閉じると消える）で、最後の操作から `session_hours` で失効します。ログイン画面で「ログインを保持する」を選ぶと、Cookie に `session_remember_days`（既定 30 日）の有効期限を付け、セッションもログインから同じ期間で失効します（操作による延長はしない）。ブラウザ用の待ち受けの GET 以外の要求には `X-Mimamori-Request: 1` を必須にしています（CSRF 対策）。
- 権限区分の変更、無効化、削除、パスワードの再設定を行ったアカウントのセッションはその時点で削除します。自分のパスワードの変更では、操作したセッション以外を削除します。
- 有効な管理者が 1 人だけの場合、その管理者の削除、無効化、閲覧者への変更は 409 です。
- 権限の判定はすべての API でセントラルが行います（`requireAny` / `requireAdmin`）。管理用の API は TCP の接続元がループバックで、CLI 用の秘密が一致する場合だけ使え、それ以外の接続元には 404 を返します。
- 操作の履歴には操作したアカウントを記録します。

## 13. フロントエンド

### 13.1 構成

- Vite + React 19 + TypeScript + Tailwind CSS v4（`@tailwindcss/vite`）+ react-router-dom + i18next。
- `yarn build` の出力 `frontend/dist` を Go バイナリに埋め込み、ブラウザ用の待ち受けで配信します。
- API の呼び出しは `src/api/client.ts`、型は `src/types.ts` にまとめています。401 を受けるとログイン画面に移り、ログイン後に元の画面に戻ります。
- ログイン中のアカウントは `src/context/AuthContext.tsx` で共有し、閲覧者には権限の無い操作を表示しません（判定はサーバーでも行う）。

### 13.2 テーマと多言語対応

- 色は `frontend/tailwind.config.js` のセマンティックトークン（`canvas`、`surface`、`ink`、`muted`、`line`、`accent`、`danger`、`warning`、`success` とその soft / hover）を `light-dark()` で定義し、OS の設定に従ってライト / ダークを切り替えます。
- 対応言語は英語と日本語（`src/i18n/en.json` / `ja.json`）です。表示言語はアカウントごとの設定（`accounts.language`）で、`auto`（自動選択）、`en`、`ja` のいずれかです。`auto` はブラウザの言語設定（`navigator.languages`）から判別し、日本語なら日本語、それ以外は英語で表示します。
- アカウントの作成時に指定します。指定が無ければ `auto` として記録します（API、CLI の `ctl accounts create --language`、`central init-admin --language`）。ブラウザ画面での作成も、初期値は `auto` です。
- 言語の設定はユーザーテーブルにだけ保存し、ブラウザには保存しません。ログイン後はそのアカウントの設定で表示し、ヘッダーの言語の切り替えはログイン中のアカウントの設定を変更します（`PUT /auth/language`）。ログイン画面はブラウザの言語から判別して表示し、そこでの切り替えはその画面の表示だけに使います。
- CLI、エージェントとセントラルのログ、通知メールは英語だけを使い、ロケールが `C`（`LANG=C`）でも動作します。トークン名やルール名など利用者が入力した値は、そのまま表示します。

## 14. 拡張の方法

audit 以外の監視機能を加える場合は、次の仕組みの上に追加します。

1. `modules.RuleContent` に種類の設定を追加し、検証とテンプレートの展開の規則（`scalarFields` または一覧の結合）を追加する。
2. `modules.DetectionTypes` に種類を追加し、`AgentRuntime.Cycle` で検知を収集して `DetectionReport` を返す。
3. トークン、適用、報告、検知の保存、抑止条件、通知、画面、アカウントの仕組みはそのまま使える。

## 15. ビルド、テスト、リリース

- Go は 1.27.4、フロントエンドのパッケージ管理は yarn 4.18.1（`packageManager`）を使います。npm は使いません。

- `make lint`: `go vet`、`staticcheck`、`golangci-lint`（`.golangci.yml`）、`yarn lint` を実行します。
- `make test`: `go test ./...`。セントラルの API（認証、権限、トークンの更新と再発行、インスタンス ID、検知の集約、抑止、通知）とモジュール（マージ、検証、パスの判定、auditd の記録の解析、走査、未送信の保存）のテストがあります。
- `make`（`make build`）: フロントエンドをビルドし、Linux（amd64 / arm64）向けにビルドして `bin/` に出力します。Linux 固有のシステムコールを使うため、他の OS 向けにはビルドしません。
- バージョンは `Makefile` の `VERSION` を `-ldflags "-X main.version=..."` で埋め込みます。
