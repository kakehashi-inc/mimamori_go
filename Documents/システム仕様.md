# システム仕様 - mimamori

各ホストで、指定した OS のユーザーの権限によって行われる操作を auditd の記録とファイルの走査で検知し、セントラルに集めて通知するシステムの設計書です。要件の定義はリポジトリ外の要件定義書、HTTP API の詳細は [API仕様.md](API仕様.md)、テーブルの詳細は [テーブル定義.md](テーブル定義.md)、コマンドと引数は [CommandReference-ja.md](CommandReference-ja.md) を参照してください。本書ではそれらの内容を繰り返しません。

## 1. 用語定義

| 用語（日本語） | English | 説明 |
| --- | --- | --- |
| セントラル | Central | 報告の受信と保存、通知、トークン、監視ルール、テンプレート、アカウントの管理、ブラウザ画面と管理用の API を提供する常駐プロセス。自ホストに対しては内蔵エージェントとしても機能する |

| 処理の流れ | Flow | アプリが作るスレッドやゴルーチンなど、並行して動く処理の単位 |

| 適用 | Apply | 監視ルールの特定の版を、指定したエージェントに割り当てる操作 |
| テンプレート | Template | 監視ルールを作るための元。組み込みのテンプレート（Built-in template）と管理者が作成したテンプレート（Custom template）がある |

| 検知 | Detection | エージェントが監視ルールに従って見つけた事象 |

| 再認証 | Re-authentication (step-up) | コマンドセットを変更する前に、ログイン中のセッションでメールの確認コードを入力し直すこと（12.5.10） |

## 2. 全体構成

```text
 monitored host                                   central host
+-----------------------------+                 +--------------------------------------------------+
| mimamori agent start        |   HTTPS (CA)    | mimamori central start                           |
|  (1 flow)                   | --------------> |  flow 1: accept + workers (default 1)            |
|  auditctl / ausearch        |                 |    HTTPS listener: agent API, admin API (CLI)    |
|  file scan                  |                 |    HTTP listener:  browser API, embedded SPA     |
|  agent.db (SQLite)          |                 |  flow 2: built-in agent (same code as the agent) |
|  data/                      |                 |  central.db, one DB per target (SQLite)          |
+-----------------------------+                 |  SMTP (company server) for notifications         |
                                                |                                                  |
 central host shell                             |                                                  |
+-----------------------------+   HTTPS (CA)    |                                                  |
| mimamori ctl ...            | --------------> |                                                  |
+-----------------------------+  agent_listen   +--------------------------------------------------+
```

- 1 つの実行ファイル `mimamori` がセントラル、エージェントの初期化と起動、CLI を提供します。
- 待ち受け、パス、認証の方法は [API仕様.md](API仕様.md) の 1.1、DB ファイルは [テーブル定義.md](テーブル定義.md) を参照してください。
- 接続はエージェントからセントラルへの一方向のみです。セントラルからエージェントへは接続しません。
- パッケージ間の依存は `main -> workers -> modules -> models` の一方向です。`workers` が `init()` で `modules.StartCentral` にセントラルの起動関数を登録します（循環参照の回避）。

## 4. 処理の流れ

### 4.1 エージェント

- `agent start` は main の 1 つの流れだけで動きます。セントラルとの通信（`httpc.go`）、auditd のツールの実行（`runner.go`）、ファイルの走査、DB と設定の保存をすべてこの流れの中で順番に行います。
- 外部コマンドは `os.StartProcess` で起動し、標準出力と標準エラーをパイプで受け取ります（ファイルは作らない）。パイプは短い読み取りの期限付きで、`wait4(WNOHANG)` を短い間隔で確認する合間に読み出し、出力の上限を超えた分は読み捨てます。タイムアウトを過ぎたらプロセスグループごと `SIGKILL` します（`os/exec` のタイムアウトのようなゴルーチンを作らない）。
- 通信は 1 リクエスト 1 接続で、接続、TLS ハンドシェイク、送受信のすべてを接続の期限（30 秒）で打ち切ります。happy eyeballs の並列接続も無効にしています。
- 1 回の処理が確認の間隔より長くかかっても、次の処理はその終了後に始まります（間隔の残りが 1 秒未満なら 1 秒待つ）。
- コマンドセット（12.5）もこの流れの中で 1 セットずつ実行します。コマンドの実行中は、その終了を待つループの中で、確認の間隔が過ぎるたびに監視の処理（同期、auditd の記録の取得、走査、報告）を行います。処理の間の待機は、次の監視の処理か、コマンドセットの次の予定の早い方で終わります。
- 終了の指示（SIGINT / SIGTERM）は、処理の区切りと待機中に確認します。処理中は、その回の処理と状態の保存を終えてから終了します。
- Go ランタイムと標準ライブラリが内部で使う補助的なゴルーチン（GC、シグナルの受け渡し、`database/sql` の接続管理、名前解決）は、アプリの処理を並列化するものではないため対象外です。アプリの処理はすべて上記の 1 つの流れで行います。

### 4.2 セントラル

| 処理の流れ | 内容 |
| --- | --- |
| セントラルの機能（main） | 2 つの待ち受けと接続を 1 回の `ppoll` で待ち、受け付け、要求の読み取り、応答の書き込みを待たずに行う。全部届いた要求と定期的な処理（30 秒ごと）を待ち行列に入れる。ワーカー数が 1（既定）のときは、この流れ自身が待ち行列の仕事を 1 件ずつ処理する |
| ワーカー（ワーカー数が 2 以上のとき） | ワーカー数と同じ数のゴルーチンが、待ち行列の要求のハンドラーと定期的な処理を実行する。ソケットには触れない（読み書きは main が行う） |
| 内蔵エージェント | エージェントと同じ `AgentRuntime` を 1 つのゴルーチンで動かす |

- 接続ごとのゴルーチンを作る `net/http.Server` は使いません。1 接続で 1 リクエストを処理し、応答は `Connection: close` で書きます。
- main は 1 回の繰り返しで、待ち受け、読み取り中と書き込み中の接続、（ワーカー数が 2 以上のとき）ワーカーが処理の終わりを知らせるパイプを、1 回の `ppoll` で待ちます。待つのは最も近い期限まで、最長 250 ミリ秒（`LoopWakeInterval`。停止の指示と定期的な処理はこの間隔以内に確かめます）で、始められる仕事があれば待ちません。その後、準備のできた待ち受けからカーネルの待ち行列にある接続をすべて受け付け（1 つの待ち受けから 1 回に最大 512。受け付けた直後に切断する接続元が接続し続けても main がここに留まらないため。開いている接続の上限に達して外せる接続が無いときは、残りをカーネルの待ち行列に残します）、準備のできた接続を待たずに読み書きし（`MSG_DONTWAIT`）、期限を過ぎた接続を拒否し、仕事を始めます。1 回の繰り返しの後、ハンドシェイクを待つ接続があれば、順番の来た 1 つの TLS ハンドシェイクを始めます（下記）。時間の制限などの値は `app/modules/constants.go` にあります。
- 要求の読み取り: ブラウザ用の待ち受け（HTTP）では、ソケットから接続ごとのバッファーに読み込みます。ヘッダー（空行まで。64 KiB（`MaxHeadBytes`）を超えると 431）が届いたら、`Content-Length` の分の本文を待ちます。不正なヘッダーは 400、`Transfer-Encoding` を使う本文は 411 を返します（ブラウザ画面、エージェント、`ctl` は `Content-Length` を送ります）。本文が上限（32 MiB）を超える要求は本文を読まずに渡し、ハンドラーはこれまでと同じ上限のエラーを返します。要求が全部届いてからワーカーに渡し、ハンドラーは本文をメモリーから読みます。要求の後ろに続くデータは無視します。
- HTTPS の待ち受けでは、最初の TLS のレコード（ClientHello）が全部届いてから TLS ハンドシェイクを行います（TLS のハンドシェイクのレコードでないデータは、届いた時点で失敗させます）。ハンドシェイクは標準ライブラリーの `crypto/tls` で行い、途中で止めて後で続けることができないため、同時に行うのは 1 つだけです。ハンドシェイクがクライアントの次の応答を待つ間（ソケットに読むデータが無いとき、または書き込めないとき）、main はハンドシェイクの読み書きの中から、ふだんと同じ 1 回の繰り返し（`ppoll` での待ち、受け付け、要求の読み取り、ワーカーへの受け渡しとワーカー数が 1 のときのハンドラーの実行、応答の書き込み、期限の処理、定期的な処理）を、その接続のデータが届くかハンドシェイクを打ち切るまで繰り返します。この入れ子の繰り返しでは新しいハンドシェイクを始めないため、入れ子は 1 段だけで、ゴルーチンも作りません。そのため、ハンドシェイクを待つのはほかのハンドシェイクだけで、HTTP の待ち受けの要求、ハンドシェイクを終えた HTTPS の要求、応答、受け付け、期限の処理は、どの接続元が止まっても遅れません。
- ハンドシェイクの制限: クライアントの次の応答を、ハンドシェイクを始めてから 2 秒（`TLSHandshakeTimeout`）まで待ちます。正しいクライアントは 1 回の往復と鍵交換の時間で応答するため（同じネットワークでは数ミリ秒、遠い拠点でも 1 秒未満）、十分な長さです。ハンドシェイクの順番を待った時間は、この制限に数えず、ハンドシェイクが成功したときは待ち行列の期限をその分延ばします（順番を待ったために正しい接続が切られることはありません）。ハンドシェイクを始める前に待ち行列の時間を過ぎた接続は、ハンドシェイクをせずに切断します。
- ハンドシェイクの順番と打ち切り: 接続元は送信元のアドレスで、ループバックのアドレスはすべて 1 つの接続元として扱います（ホストのプロセスは 127.0.0.0/8 のどのアドレスでも使えるため）。ClientHello が届いた接続のうち、最近止まっていない接続元の最も古い接続を先に、それが無ければ最近止まった接続元の最も古い接続を行います。「最近止まった」は、その接続元のハンドシェイクを打ち切ってから 60 秒（`HandshakePenalty`）以内であることです。行っている最中のハンドシェイクは、次の表のときに打ち切ります（接続を閉じます）。表の「待つ接続」は、ClientHello が届いて順番を待っているほかの接続（同じ接続元のものも含みます。切断する接続元の接続と、待ち行列の時間を過ぎた接続を除きます）です。

  | 行っているハンドシェイクの接続元 | 待つ接続 | 打ち切る時刻 | 接続元について覚えること |
  | --- | --- | --- | --- |
  | 最近止まっていない | 無い | 開始から 2 秒 | 止まった（制限まで使った） |
  | 最近止まっていない | ある | 開始から 0.4 秒（`HandshakeGrace`） | 止まった（順番だけ） |
  | 最近止まった | 無い | 開始から 2 秒 | 止まった（制限まで使った） |
  | 最近止まった | 最近止まった接続元（同じ接続元を含む）のものだけ | 開始から 0.4 秒 | 止まった（順番だけ） |
  | 最近止まった | 最近止まっていないほかの接続元のものがある | すぐ | なし |
  | どれでも | （停止の指示） | すぐ | なし |

  0.4 秒は、正しいクライアントの 1 回の往復と鍵交換に足りる長さです（遠い拠点でも）。最近止まった接続元同士では、すぐではなく 0.4 秒で打ち切ることで、止まる接続元のために、同じく後回しになっている別の接続元の正しいクライアントが切られないようにしています。2 秒の制限まで待つのは、後ろに待つ接続が 1 つも無いハンドシェイク（応答の遅い正しいクライアントを含む）だけです。2 秒の制限まで使った接続元のうちホストの外のアドレスは、その 60 秒間、HTTPS の待ち受けで受け付けた直後に切断し、ログに出します。ループバックのアドレスとホスト自身のアドレス（接続先のアドレスにかかわらず、ホストのどのインターフェースのアドレスでも。`net.InterfaceAddrs` で取得し、1 秒より古ければ取得し直すため、後から付けたアドレスも 1 秒以内に対象になります）からの接続は切断せず、後回しにするだけです。0.4 秒で打ち切った接続元も、後回しにするだけです（どちらもログに出します）。
- 残る制限: ほかの接続元の止まった接続と同時に届いた正しい TLS の接続は、その前にある、初めて止まる接続元 1 つにつき最長 0.4 秒待ちます（初めて止まる接続元が 20 あれば 8 秒で、既定の待ち行列の時間 10 秒に収まります。それより多いと、待ち行列の時間を過ぎて切断されることがあります）。止まった接続元の接続は、その後 60 秒間、ほかに待つ接続が無いときにだけ行い、待つ接続が現れればすぐ打ち切るため、ほかの接続元を遅らせません。止まる接続元と同じ接続元からの接続（ループバックでは、ホストのすべてのプロセスの接続）は、止まった接続の後ろで、その 1 つにつき 0.4 秒待ちます（前に 25 ほどを超えると、待ち行列の時間を過ぎて拒否されます）。その 60 秒間は、止まった接続元の正しいクライアント（同じアドレスを共有する NAT の後ろのクライアントや、止まった後のホストの ctl と内蔵エージェントを含みます）のハンドシェイクも、ほかの接続元の ClientHello が届くとすぐ打ち切られます。また、同じ接続元のほかの接続が順番を待っているハンドシェイクは 0.4 秒で打ち切るため、往復の時間が 0.4 秒に近い遠いクライアントが同時に複数の接続を開くと、切られることがあります。
- ハンドシェイクの後は、届いた暗号文をバッファーに入れて `crypto/tls` で復号し、HTTP と同じように要求の全体を待ちます。応答も暗号化し、続けて TLS の close_notify の警告（接続を閉じる知らせ）を付けて、接続のバッファーに入れます。
- 応答の書き込み: ハンドラーの応答はメモリーにできています。main がソケットの受け付ける分ずつ書き、全部書いたら接続を閉じます。読むのが遅いクライアントも、全体の制限の間は切りません。
- 時間の制限:
  - 受け付けてからヘッダーが届くまで（HTTPS ではハンドシェイクを含み、ハンドシェイクの順番を待った時間を除く）と、64 KiB 以下の本文: 待ち行列の時間（`queue_timeout_sec`、既定 10 秒）。何も送らない接続、ヘッダーや ClientHello の途中で止まった接続、本文を送らないログインの要求は、ワーカーを使わずに待ち、この時間を過ぎると拒否されます。
  - 64 KiB を超える本文（エージェントの報告など）: ヘッダーが届いてから 60 秒（`ConnTotalTimeout`）。この本文の受信にかかった時間は、待ち行列の時間に数えません。このような本文は、認証された要求からだけ読みます（下記の「大きな本文と認証」）。
  - 全部届いた要求がワーカーを待つ時間: 待ち行列の時間（上記の本文の受信の時間を除く）。
  - 応答の書き込み: ヘッダーが届いてから 60 秒（`ConnTotalTimeout`）。
  - 時間を過ぎた接続は拒否します（応答は [API仕様.md](API仕様.md) の 1.2）。応答の書き込みが終わらない接続は閉じます。
- 開いている接続は 256 まで（`MaxPendingConns`）です。上限に達しているときは、答えを書き終えて読み捨て中の接続（下記）を閉じ、それが無ければヘッダーをまだ送り終えていない接続（HTTPS ではハンドシェイクの前を含む。行っている最中のハンドシェイクは外しません）のうち最も古いものを拒否して新しい接続を入れます。そのような接続が無ければ、ほかに相手を待っている接続（64 KiB を超える本文を受信中の接続は 503 で拒否、応答を書き込み中の接続は閉じる）のうち最も古いものを外します。外すのは、その状態で 1 秒（`EvictGrace`）以上待っている接続だけです（同時に多くのクライアントが接続したとき、要求を送っている途中の接続を外さないため）。外せる接続が無い（すべてが処理を待つか処理中か、待ち始めたばかりの）ときは、新しい接続を受け付けずにカーネルの待ち行列（512）に残し、空きができたときに受け付けます。待ち行列の時間は、受け付けたときから数えます。
- メモリーの上限: 各接続は 64 KiB までは常に読み込めます。それを超える本文は、すべての接続がバッファーに持つ量の合計が 128 MiB（`MaxBufferedBytes`）未満の間だけ読みます。上限に達すると読み取りを止め、送信側は TCP のフロー制御で待ちます（その接続の期限は変わりません）。要求のためのメモリーは、およそ 128 MiB と 256 × 64 KiB（16 MiB）に、書き込み中の応答を足した量までです。バッファーは倍々に大きくし、使わなくなった領域はガベージコレクションまで残るため、プロセスの常駐メモリーはこの 2 倍程度になります（256 の接続がそれぞれ上限に近い本文を送り続けた計測で約 250 MB）。
- 大きな本文と認証: ヘッダーが 64 KiB を超える本文を予告した要求は、本文を読む前に、その経路に対して認証されているかを確かめます。エージェント用の経路はトークンとインスタンス ID、管理用の経路（`/admin/v1`）はホストからの接続であることと CLI の秘密の値、ブラウザ用の API はログインセッション、CSRF のヘッダー、そのアカウントの経路があることです。本文で認証する経路（ログイン）と、それ以外の経路は、大きな本文を受け付けません。認証されていない要求は、本文を読まずにすぐハンドラーに渡し、ハンドラーが未認証の要求への通常の答え（401 など）を返します。この確認は読むだけで（トークンの使用の記録、インスタンスへの結び付け、セッションの延長や削除、履歴への記録はしません）、ハンドラーがそれらを 1 回だけ行います。確認は main で行うため、ワーカーの処理と同時に動いても安全な処理（データベースの読み取りと、起動後に変わらない値）だけを使います。ワーカー数が 4 以上のときは、確認のデータベースの読み取りが、ワーカーの問い合わせが終わってデータベースの接続（最大 4）が空くのを待つことがあり、その間 main は止まります。確認の後、ハンドラーの前に認証の状態が変わった場合は、ハンドラーの判断に従います（本文は読まれていないため、本文の読み取りの誤りになります）。
- 読み終えていない要求への答え: 要求を最後まで読まずに答えた接続（不正なヘッダー、上限を超える本文、認証されていない大きな本文、要求の途中での 503）は、答えを書き終えたら送信側を閉じ（`shutdown`）、届くデータを最長 5 秒（`DrainTimeout`）、最大 64 MiB（`DrainMaxBytes`）まで読み捨ててから閉じます。読み残しのある接続をすぐに閉じると接続がリセットされ、送り終えてから答えを読むクライアントが答えを受け取れないためです。読み捨ては main が待たずに行い、1 回の繰り返しで 1 つの接続から最大 1 MiB を読みます。
- main が仕事（ワーカー数が 1 のときのハンドラー、ハンドシェイクの計算）をしている間に届いた接続はカーネルの待ち行列で待つため、その時間も待ち時間に数えます（`ppoll` が 1 ミリ秒を超えて待ったときは `ppoll` に入った時刻から、そうでないときは前回の `ppoll` が戻った時刻から数えます）。毎回、待ち受けにある接続をすべて受け付けるため、待ち時間は届いたときから数えることになり、ハンドシェイクを待つ接続にも待ち行列の時間が当てはまります。
- 相手を待ってほかの処理を止めるものはありません。ハンドシェイクだけは 1 つずつ行うため、最悪の場合、ほかのホストの 1 つの接続元がほかの接続元のハンドシェイクを遅らせるのは、60 秒に 1 回、最長 0.4 秒です（ほかに待つ接続が無いときに 2 秒の制限まで使うと、その後 60 秒間切断されます）。N 個の接続元からは 60 秒に N × 0.4 秒です（IPv6 ではアドレスごとに数えます）。ループバックとホスト自身のアドレスは切断しませんが、止まった後のハンドシェイクは、ほかに待つ接続があればすぐ打ち切ります。何も送らない接続、途中で止まる接続、応答を読まない接続は、ほかの要求を遅らせません。ワーカー数が 1 のときは、ハンドラーの処理時間（ログインのパスワードの照合など）も順に待つため、同時に多くの要求が届くとその合計だけ遅れます（ハンドシェイクの最中にハンドラーを実行したときも同じで、そのハンドシェイクのソケットはハンドラーの後に読みます。その間にハンドシェイクの制限や 0.4 秒を過ぎても、打ち切る前にソケットをもう一度確かめ、届いていたクライアントの応答は受け取ります。この確認は 1 つのハンドシェイクにつき 1 回のため、1 バイトずつ送り続ける接続も制限で終わります）。
- ワーカー数が 2 以上のときは、main が全部届いた要求（本文、`RemoteAddr`、`req.TLS`、接続のローカルアドレスを含む）をワーカーに渡し、ワーカーは応答をメモリー上で作って main に返します。ソケットの読み書きと TLS の暗号化と復号は main だけが行います。
- 停止の指示を受けると（ハンドシェイクの最中に受けたときは、そのハンドシェイクを打ち切ってから）、処理を始めていない接続を拒否し、処理中の要求を終えて応答を書いてから（最長 5 秒、`StopFlushTimeout`）、すべての接続を閉じます。
- 定期的な処理も待ち行列の仕事として扱うため、ワーカー数の範囲内で動きます。同時に 2 つは動きません。
- SMTP との通信は接続の期限（既定 30 秒）で打ち切ります。
- 内蔵エージェントと、同じホストで別に起動したエージェント（`agent start`）は、同じキー `mimamori` の auditd のルールと同じルールファイル（`/etc/audit/rules.d/zz-mimamori.rules`）を使います。そのため、1 つのホストではどちらか一方だけを使います。
- `builtin_agent` が `false` でセントラルを起動したとき、内蔵エージェントのローカル DB（`builtin-agent.db`）に適用した監視ルールか適用の結果、または記録した全体の設定があれば、キー `mimamori` の auditd のルールとルールファイルを 1 度だけ削除し、全体の設定を記録した値に戻し（9.2 の最後）、その記録を消して、内蔵エージェントの適用の結果を `none` にします（履歴 `apply_result_none`）。記録が無い場合（DB が無い場合を含む）は、同じホストで別のエージェントが動いている可能性があるため、auditd のルールに触れません。削除に失敗した場合はログに出し、記録を残して次の起動で再び試みます。

### 4.3 起動と終了

- エージェントの起動前の確認: auditd のツール（`auditctl`、`ausearch`）が使える、`auditctl -s` で auditd が動いていて（`pid` が 0 でない）監査が有効（`enabled` が 0 でない）、`auditctl -l` が成功する、`agent.db` があり、設定（接続先、トークン、独自 CA、インスタンス ID）がそろっている。満たさなければ起動しません。
- 実行ユーザーを root に限定する確認は行いません。必要な権限（auditd の操作、`/etc/audit/rules.d/zz-mimamori.rules` の書き込みと削除、監査ログの読み取り、データディレクトリの読み書き、プロセスへのシグナル）は、それぞれの操作の結果で判断し、足りなければその操作のエラーとして報告します。なお、`auditctl` は多くのディストリビューションで root 以外の実行を拒否するため、エージェントと内蔵エージェントは実質的に root での実行になります。セントラルの機能、`status`、`stop`、`init-admin`、`reset-password`、`central config`、`agent set-central`、`ctl` は、データディレクトリなどへの権限があれば root 以外でも動作します。
- 多重起動は、データディレクトリのロックファイル（`agent.lock` / `central.lock`）への `flock(LOCK_EX|LOCK_NB)` で防ぎます。`status` と `stop` が確認のために一瞬だけ掛ける共有ロックと重なっても起動に失敗しないよう、ロックを取れない場合は 0.1 秒の間隔で 5 回まで試してから多重起動として終了します。起動したプロセスはロックファイルに自分のプロセス ID を書きます。
- 常駐は supervisor などから行い、終了は SIGTERM（または SIGINT）で指示します。`central stop` / `agent stop` は、ロックファイルを保持しているプロセスに SIGTERM を送り、プロセスが処理の区切りで終了してロックを解放するまで待ちます（待ち時間と終了コードは [CommandReference-ja.md](CommandReference-ja.md)）。
- `central status` / `agent status` は、ロックファイルを保持しているプロセスの有無で稼働中かを判定します（表示する内容と終了コードは [CommandReference-ja.md](CommandReference-ja.md)）。ロックファイルは読むだけで変更しません。セントラルは起動してロックを取得し設定を読み込んだ時点で、再起動で反映する項目（`web_listen`、`agent_listen`、`workers`、`queue_timeout_sec`、`builtin_agent`）の起動時の値を central.db の settings の `running_config` に保存し、停止するときに消します。`central status` は、稼働中ならこの値を表示し、保存済みの設定と違う項目には保存済みの値と再起動後に反映することを併記します。停止中、またはこの値が無い場合は保存済みの設定を表示します。
- セントラルは起動時に auditd を確認し、使えない場合もセントラルの機能は起動して内蔵エージェントだけを停止状態にします。理由はログ（1 行）と、画面の上部の警告（`GET /overview`）に表示します。設定（`builtin_agent`）で無効にしている場合は、内蔵エージェントについてのログを出力せず、画面の警告も表示しません（4.2 の auditd のルールの削除についてのログを除く）。
- エージェントは起動時に、保存している監視ルールを適用し直します（再起動や auditd の再起動で OS 標準のルールが読み込み直されるため）。

## 5. CLI

コマンド、引数、終了コードは [CommandReference-ja.md](CommandReference-ja.md) を参照してください。ここでは CLI の動作の仕組みだけを記載します。

- `ctl` は設定を持ちません。管理用の API はセントラル自身の待ち受けなので、接続先はセントラル管理用 DB の設定 `agent_listen` から、CA 証明書はデータディレクトリの `ca.crt` から決めます。接続先のアドレスは、`agent_listen` のアドレスがすべてのアドレスなら、空と `0.0.0.0` では `127.0.0.1`、`::` では `::1`（IPv6 のすべてのアドレスの待ち受けが IPv4 の接続を受けるかは OS の設定 `net.ipv6.bindv6only` によるため）、特定の IP アドレス（ループバックかどうか、IPv4 か IPv6 かを問わない）ならその IP アドレスで、ポートは `agent_listen` のポートです。サーバー証明書には待ち受けのアドレスが含まれるとは限らないため、どのアドレスに接続しても、証明書は常に含まれる名前 `127.0.0.1` で CA に対して検証します（検証は省略しません）。
- 管理用の API は、接続元のアドレスがループバックのアドレスであるか、接続元の IP アドレスがその接続を受け付けた自分側の IP アドレスと同じ（このホストから自分のアドレスへの接続）場合だけ使えます。判定には TCP の接続の両端のアドレスだけを使い、ヘッダーは使いません。`agent_listen` を変更してセントラルを再起動するまでの間は、CLI は新しいポートに接続するため使えません（画面に「再起動待ち」と表示される）。
- セントラルは起動のたびに新しい CLI 用の秘密を作ってデータディレクトリの `cli.secret`（0600）に書き、`ctl` はそれを読んで管理用の API に接続します。`ctl` を使えるのは、そのファイルを読める OS ユーザーだけです。入力や設定は要りません。
- 履歴の操作者は、`ctl` の操作では `cli` と記録します。セントラルのホストでセントラル管理用 DB を直接操作するコマンド（`central init-admin`、`central reset-password`、`central config set`、`central config unset`）では、`local:<OS のユーザー名>`（`/etc/passwd` に無ければ `local:uid <番号>`）と記録します。
- このアプリ独自の環境変数はありません（設定は DB に保存し、コマンドと引数で行います）。外部コマンド（`auditctl`、`ausearch`、`ctl rules edit` のエディタ、コマンドセットを実行する `bash` などの外部コマンド）は `PATH` から探して起動し、このプロセスの環境を引き継ぎます。出力を解析する `auditctl` と `ausearch` だけは、出力の形式と時刻の解釈が利用者の設定に左右されないよう、`LC_ALL=C`、`TZ=UTC` に置き換えて起動します。表示の時刻は通常のローカル時刻（`TZ`、無ければ `/etc/localtime`）です。
- コマンドラインの誤り（不明なコマンドやフラグ、値の不足や形式の誤り）は、使い方とエラーを表示して終了します（終了コードは [CommandReference-ja.md](CommandReference-ja.md)）。
- `--data-dir` を省略した場合のデータディレクトリは [CommandReference-ja.md](CommandReference-ja.md) のとおりです。`--data-dir` の空の値を引数エラーにするのは、カレントディレクトリにならないようにするためです。実行ファイルの場所は起動時のパス（`argv[0]`。シンボリックリンクはたどる）から求め、`/proc` や `PATH` は使いません。

## 6. 設定と保存場所

設定ファイルはありません。設定もデータも、データディレクトリ（[CommandReference-ja.md](CommandReference-ja.md) の `--data-dir`）の SQLite に保存します。このアプリが作成、更新、削除するファイルは、データディレクトリの中と auditd のルールファイル（`/etc/audit/rules.d/zz-mimamori.rules`）だけです（外部コマンドの出力はパイプで受け取り、SQLite の一時データはメモリに置き、CLI の編集用の一時ファイルは `data/` に作る）。それ以外は読むだけです。読むのは、監視と自ホストの情報（`/etc/passwd` は履歴の操作者名にも使う）のための `/etc/passwd`、`/etc/group`、`/etc/os-release`、`/etc/audit/auditd.conf`、監査ログ、監視ルールで指定した走査の対象、監視ルールの適用の前に存在を確認する監視ルールのディレクトリと実行ファイルと走査の起点、`/etc/audit/rules.d`、`ctl` の `--file` で指定したファイルです。セントラルとエージェントのデータファイルは名前が重ならないため、同じ `data/` を使えます（auditd のルールは 4.2 のとおり共有できません）。実行ファイルのディレクトリ自体の所有者と権限は変更も確認もしません。

DB ファイル（セントラル管理用 DB、監視対象ごとの DB、エージェントのローカル DB）は [テーブル定義.md](テーブル定義.md) を参照してください。それ以外のファイルは次のとおりです。

| ファイル | 内容 |
| --- | --- |
| `ca.crt` | CLI が使う独自 CA の公開の証明書（0644） |
| `cli.secret` | CLI 用の秘密（0600、セントラルの起動のたびに作り直す） |
| `central.lock`、`agent.lock` | 多重起動の防止と、`stop` / `status` で動いているプロセスを見つけるため |

データディレクトリは無ければ 0700 で作ります。既存の場合は、何も変更せず、確認もしません。読み書きできるかは実際のアクセス権で決まり、できなければそのエラーで止まります。

セントラルの設定は、管理者がブラウザの「システム設定」画面（`/config`）または `central config` で変更します。保存していない項目は既定値です。保存時の検証と履歴は [API仕様.md](API仕様.md) の「システム設定」のとおりで、検証の内容は下の表のとおりです。検証は保存と同じ書き込みのトランザクションの中で、保存されている値に対して行います。空の値は、空に意味がある項目（`server_names`、`smtp.host`、`smtp.username`、`smtp.password`、`smtp.from`、`smtp.helo_name`）だけ受け付け、それ以外はエラーにします。文字列の項目は制御文字（改行、NUL など）を受け付けません。保存済みの値が不正な場合（以前の版で保存した値など）は、セントラルが起動せず、`central config` で 1 項目ずつ直せます（すでにある不正を理由には変更を拒否せず、新しい不正を加える変更だけを拒否します）。検証で拒否した変更（`modules.Msg` または `modules.Problems` のエラー）は 400 で答え、それ以外の失敗（データベースの読み書きの失敗）は内部エラー（500）として答えます（データベースの文は画面に出さず、ログに残します）。

- 既定のポート（ブラウザ用 9080、エージェント用 9081）は `app/modules/constants.go` の `DefaultWebPort`、`DefaultAgentPort` だけで決まり、既定の待ち受け、エージェントの `--central-port` の既定、画面の例はそこから作ります。
- 項目ごとの反映の時期（即時か、再起動後か）は [CommandReference-ja.md](CommandReference-ja.md) の `central` のとおりです。再起動後に反映する項目は、動いているセントラルが起動時の値を使い続け、画面では保存した値と使っている値が異なる項目を「再起動待ち」と表示します。
- `server_names` を変えると、次の確認でサーバー証明書を発行し直します。

| 項目 | 既定値 | 説明 |
| --- | --- | --- |
| `web_listen` | `0.0.0.0:9080` | ブラウザ用の待ち受け（HTTP）。アドレスは IP アドレスで指定する（待ち受けはシステムコールで作り、`/proc` を読まないため名前解決もしない）。ポートは 1 から 65535 |
| `agent_listen` | `0.0.0.0:9081` | エージェントおよび管理用の待ち受け（HTTPS）。IP アドレスで指定する。ポートは 1 から 65535。`web_listen` と同じ値は使えない。`ctl` はこのアドレス（空と `0.0.0.0` なら `127.0.0.1`、`::` なら `::1`）とポートに接続する（5 章） |
| `server_names` | なし | サーバー証明書に含めるホスト名と IP アドレス（カンマ区切り）。`127.0.0.1`、`::1`、`localhost` は常に含める。各要素は IP アドレス（標準の表記で保存）か、英数字とハイフンのラベルから成る ASCII のホスト名（小文字で保存、253 文字まで）。証明書を作り直すかの判断も正規化した名前で比べる |
| `workers` | 1 | リクエストを処理するワーカーの最大数（64 まで） |
| `queue_timeout_sec` | 10 | 待たせた接続を拒否するまでの時間（3600 まで） |
| `token_valid_days` | 365 | トークンの有効期間の既定値（36500 まで） |
| `token_renew_before_days` | 30 | 残りの有効期間がこれを下回ったら自動更新する（`token_valid_days` より小さい値に限る） |
| `retention_days` | 180 | 検知、拒否した接続の履歴、コマンドセットの実行の保存期間（36500 まで） |
| `default_check_interval_sec` | 60 | 監視ルールが無いエージェントの確認の間隔（10〜3600） |
| `session_remember_days` | 30 | 「ログインを保持する」を選んだ場合のセッションの有効期間（ログインから。365 まで） |
| `two_step_trust_days` | 30 | ログインの確認コードの入力で「このブラウザを信頼する」を選んだブラウザが、コードなしでログインできる日数（1〜365。即時に反映し、信頼済みのブラウザにも現在の値を当てはめる） |
| `builtin_agent` | true | 内蔵エージェントを使うか |
| `notify.min_interval_min` | 30 | 通知の最小間隔（全体で 1 通。43200 まで） |
| `notify.dedupe_hours` | 24 | 同じエージェントの同じ検知を再送しない期間（8760 まで） |
| `notify.max_lines` | 200 | 本文の行数の上限（10000 まで） |
| `notify.subject_prefix` | `[mimamori]` | 件名の接頭辞 |
| `smtp.host` / `smtp.port` | なし / 587 | SMTP サーバー（`smtp.security` により 587 / 465 / 25）。ホストはホスト名か IP アドレス、ポートは 65535 まで。`smtp.host` が空の間は開発モード（12.4）で、通知を送らず、確認コードも求めない |
| `smtp.security` | `starttls` | `starttls` / `tls`（接続時から）/ `none` |
| `smtp.auth`、`smtp.username`、`smtp.password` | false | 認証の有無と認証情報。暗号化無し（`none`）では LOGIN（Go の `net/smtp` は暗号化されていない接続で PLAIN を送らないため）、`tls` / `starttls` では PLAIN。`smtp.password` は引数では受け取らず、端末から読む場合はエコーしない（読む場所は [CommandReference-ja.md](CommandReference-ja.md) の `central config set`）。一覧では値を表示しない |
| `smtp.from` | なし | 送信元。表示名の無いメールアドレス 1 つ。通知メールの宛先は設定ではなく、12.2 のとおり通知先として選んだアカウントです |
| `smtp.timeout_sec`、`smtp.helo_name` | 30、なし | タイムアウト（3600 まで）と HELO/EHLO で送る名前（空なら `localhost`） |

プログラムは起動時に umask を 077 にし、作成するファイルとディレクトリを実行ユーザー以外が読み書きできないようにします（DB は作成時から 0600 で、SQLite は `-wal` / `-shm` を DB ファイルと同じ権限で作ります）。既存のディレクトリとファイルの所有者と権限は、変更も確認もしません（DB を開くときも変更しない）。

SQLite は URI 形式（`file:`）で開き、パスの `%`、`?`、`#` はエスケープします。このため、データディレクトリのパスにこれらの文字や空白を含んでも、DB はそのパスに作られます。

### 6.0 セントラルの移設

- 設定とデータはすべてデータディレクトリにあり、このアプリのファイルの場所は DB に絶対パスで保存しません（監視対象ごとの DB は `agents.db_file` にファイル名だけを保存し、データディレクトリからの相対で開く）。実行ファイルの場所は起動時に求めます。このため、停止したセントラルのディレクトリを移せば（実行ユーザーが読み書きできること）、別のパスや別のホストでもそのまま動作します（SQLite の `-wal` / `-shm` も含めて移すか、停止後に移す）。
- 起動時に作るもの（`cli.secret`、`ca.crt`、ロックのファイル）は作り直します。独自 CA、サーバー証明書、トークン、セッションは DB にあるため、エージェントとブラウザのログインはそのまま使えます。
- エージェントは保存したセントラルのホスト名とポート（[テーブル定義.md](テーブル定義.md) の `state`）に接続します。ホスト名が新しいホストを指すようにするか、`agent set-central` で接続先を変えます（新しいホスト名や IP アドレスは `server_names` に含める）。
- 内蔵エージェントは起動時に監視ルールを新しいホストの auditd に適用し直します。元のホストの `/etc/audit/rules.d/zz-mimamori.rules` は残ります。

### 6.1 データベースとマイグレーション

DB ファイルの種類、マイグレーション、テーブルは [テーブル定義.md](テーブル定義.md) を参照してください。

### 6.2 時刻

- 保存の形式は [テーブル定義.md](テーブル定義.md)、API の形式は [API仕様.md](API仕様.md) を参照してください（いずれも UTC）。
- 表示はローカル時間です。ブラウザ画面はブラウザのタイムゾーン、CLI（`ctl`）と通知メールとエージェントのログはそのホストのタイムゾーンで表示します。CLI が変換するのは日時の項目（`at`、名前が `_at` または `ctime` で終わる項目、`not_before`、`not_after`、`locked_until`、`switch_after`、`scheduled_for`）と、トークンと証明書の履歴の詳細の文中に含まれる日時（システムが書いたもの）だけです。ブラウザ画面の履歴も同じです。検知の対象やコメント、それ以外の分類の履歴の詳細など、利用者が入力した文字列は、日時の形を含んでいてもそのまま表示します。CLI の `--json` の出力は API の値（UTC）のままです。
- コマンドセットの定義ファイル（`ctl command-sets create` / `update`）の日時を指定した 1 回の日時は、オフセットを省略すると CLI を実行したホストのローカル時間として解釈して、そのオフセット付きで送ります。`ctl command-sets export` は、その日時をローカル時間のオフセット付きで出力します。
- `ctl detections list` の `--from` / `--to` は、CLI を実行したホストのローカル時間として解釈し、UTC の RFC3339 にしてセントラルに送ります（RFC3339 で指定した値は、そのオフセットのとおりに解釈します）。セントラルのタイムゾーンには左右されません。
- 表示や保存の長さの上限で文字列を切る場合は、文字の途中では切りません（CLI の表と通知メールは文字数、検知の対象などの保存の上限はバイト数で数えます）。

## 7. 監視ルール

### 7.1 内容

監視ルールは値だけを持ち（`modules.RuleContent`）、auditd のルールの文字列や auditd 全体の設定は含められません。未知の項目は拒否します。項目、既定値、種類ごとに監視を行う条件は [API仕様.md](API仕様.md) の 6 章を参照してください。

- `exclude_interactive` が有効な場合（未指定も有効として扱います）は、`auid` が未設定のプロセス（ログインした利用者の操作でも cron のジョブでもないもの）だけを対象にします。実行、拒否された操作、読み込みに適用し、通信には適用しません（9.1）。

検証（保存時、テンプレートの保存時、エージェントでの適用前）: パスは絶対パスで `.`、`..`、空白（どの文字体系のものも）、制御文字、引用符を含まない、書き込みを許可するパスと正当な配置場所はディレクトリ名の並び、拡張子は `.` と英数字 1-15 文字、OS のユーザー名の形式。件数、間隔、分類の範囲は [API仕様.md](API仕様.md) の 6 章のとおりです。

### 7.2 テンプレートの展開

- 一覧の項目（OS のユーザー、ディレクトリ、実行ファイル、書き込みを許可するパス、拡張子、正当な配置場所）は、テンプレートの順に合わせて重複を除きます。同じ要素で `if_missing` が異なる場合は `warn` を採用します。
- 単一の値の項目が複数のテンプレートで異なる場合は衝突とし、管理者が項目ごとに採用するテンプレートを選んで作成します（要求と応答は [API仕様.md](API仕様.md) の 6 章）。正当な配置場所は、パスと拡張子が同じで分類が異なる場合に衝突とします。
- 展開した内容は新しい監視ルールの版 1 としてコピーするため、テンプレートを後で変更しても監視ルールは変わりません。

### 7.3 保存と適用

- 保存（`PUT /rules/{id}`）のたびに `rule_versions` に新しい版を追加します。エージェントには届きません。
- 適用（`POST /rules/{id}/apply`）は `agents.assigned_rule_id / assigned_rule_version` を更新します。同期の応答には割り当て中の版を毎回含め、エージェントは動作中の版と異なる場合だけ適用します。
- エージェントの一覧と詳細に表示する版は [API仕様.md](API仕様.md) の 4 章（`AgentSummary.rule`）のとおりです。適用中の監視ルールの削除は [API仕様.md](API仕様.md) の 6 章のとおり拒否します。

## 8. エージェントとセントラルの通信

### 8.1 初期化（agent init）

1. auditd が存在して動いており、`auditctl`、`ausearch` が使える（4.3 のエージェントの起動前の確認と同じ auditd の条件）
2. 初期化済み（`agent.db` に設定がある）の場合は `--overwrite` がある。`agent.db` がある場合は、エージェントのロック（`agent.lock`）を取り、エージェントが動作中なら拒否する（動作中のエージェントは自身の持つ設定を書き戻すため）
3. トークンを読む（読む場所は [CommandReference-ja.md](CommandReference-ja.md) の `agent init`。引数や環境変数では受け取らない）
4. データディレクトリ（無ければ途中のディレクトリも含めて 0700 で作る）と `agent.db` を用意する（トークンがインスタンス ID に結び付く前に、保存場所を使えることを確かめる）
5. `GET /agent/v1/ca` を証明書の検証無しで呼んで独自 CA を受け取り、以後はその独自 CA だけを信頼して `POST /agent/v1/sync` でトークンとインスタンス ID を送って認証する（`--ca-fingerprint` を指定した場合は、受け取った証明書のうちフィンガープリントが一致したもの 1 つだけを信頼する。一致するものが無ければ失敗する。指定しない場合は受け取ったものをすべて信頼する。初回ならトークンがインスタンス ID に結び付く。インスタンス ID は初回の初期化で作り、再初期化では `agent.db` にあるものを使い続ける）
6. 設定を 1 つのトランザクションで保存する

途中で失敗した場合は、この実行で作ったもの（データディレクトリとその途中のディレクトリ、`agent.db`、ロックのファイル）を削除し、前からあったものは残します（再初期化では既存の設定を変更しません）。セントラルの証明書を検証できない場合は、接続先のホストが証明書の名前（`server_names`）に無いのか、証明書が独自 CA と一致しないのかを区別して表示します。成功したら、auditd.conf にホストを停止させる設定（`space_left_action`、`admin_space_left_action`、`disk_full_action`、`disk_error_action`、`overflow_action` が `halt` / `single`）があれば警告し、トークン名、有効期限、適用されている監視ルール（無ければその旨）、独自 CA のフィンガープリントを表示します。

### 8.2 定期的な処理

1. `POST /agent/v1/sync`: 適用中の監視ルールと版、信頼している独自 CA、最後の適用の結果を送る。応答の監視ルールの版が変わっていれば適用する。応答に新しいトークンや独自 CA があれば `agent.db` に保存する
2. auditd の記録から前回の続きの検知を取得する（監視ルールに auditd を使う種類がある場合）
3. ファイルを走査する（書き込み可能な状態の走査はその間隔ごと）
4. 検知、自ホストの情報、適用の結果をまとめて未送信の報告に入れ、古い順に `POST /agent/v1/report` で送る

- 監視ルールが無いエージェントは監視を行わず、自ホストの情報だけを報告します。走査の起点の既定値は無く、ディレクトリの構成は適用中の監視ルールに走査の起点がある場合だけ報告します。
- 同期の応答に監視ルールが無く（管理者が割り当てを外した。[API仕様.md](API仕様.md) の `POST /rules/unassign`、`ctl rules unassign`）、エージェントが監視ルールか適用の結果を保存している場合は、読み込んだキー `mimamori` の auditd のルールとルールファイルを削除して全体の設定を記録した値に戻し（9.2 の最後）、保存している監視ルールと適用の結果を消して、適用の結果 `none`（何も適用していない）を報告します。セントラルは適用中の監視ルールを無しとして表示します。削除に失敗した場合は監視ルールを残したままエラーを報告し、次の確認で再び削除します。`agent init --overwrite` は保存している監視ルールを消し、適用の結果を `pending` にするため、次の同期で、割り当てられた監視ルールを適用するか、割り当てが無ければ同じように削除します。
- 適用の結果のメッセージと注意、受け取らなかったコマンドセットの理由は、英文に加えて、コードとパラメーターで表したメッセージ（[API仕様.md](API仕様.md) の 14 章の `message_i18n`、`warnings_i18n`、`problems_i18n`。原因は入れ子のメッセージ、auditctl や OS の文はそのままの文）も報告します。セントラルは英語にすると英文と一致するものだけを保存し（適用の結果は `agents.apply_i18n`、コマンドセットは `agents.command_problems`）、画面はこれを表示の言語で表示します。これらを送らない以前の版のエージェントの結果は英文のまま表示し、以前の版のセントラルはこれらを無視します。
- 接続できない間は、最後に適用した監視ルールで監視を続け、報告をローカル DB に保存して次回にまとめて送ります（古い報告の整理は [テーブル定義.md](テーブル定義.md) の `outbox`）。保存する検知は 10,000 件までで、超えたら `normal` の検知から古い順に捨て（それでも超える場合は `alert` を古い順に）、捨てた件数を次の報告で送ります。セントラルは累計を表示し、履歴に残します。
- 同期では、保持しているコマンドセットの定義の署名を送り、応答で新しい定義と手動の実行の指示を受け取ります。報告では、コマンドセットの実行の結果、指示への応答、定義を受け取った結果を送ります（12.5）。
- 接続できないままトークンの期限が近い場合、トークンを拒否された場合（期限切れ、失効、再発行、インスタンス ID の不一致）、証明書を検証できない場合（CA の切り替えに間に合わなかった）は、エージェント自身のログ（標準エラー）に出力します。

### 8.3 認証と拒否

- 要求のヘッダーと拒否の応答は [API仕様.md](API仕様.md) の「エージェント用の API」を参照してください。
- 拒否した要求は、履歴（`rejected`）に接続元と理由を残します。同じ接続元、理由、トークン名の拒否は 10 分以内なら 1 行の回数にまとめます。

### 8.4 トークンの自動更新

- 同期の時点で残りの有効期間が `token_renew_before_days` を下回っていれば、新しい値を応答に含めます。渡し済みの新しい値が無いか、その期限が切れている場合だけ、`renew_counter` を増やし、新しい値を `HMAC-SHA256(server_key, "token-renewal:<id>:<counter>")` から導出して、そのハッシュを `pending_hash` に保存します。新しい値の有効期限は、作った時点から `token_valid_days` です。
- 未使用のまま期限が切れた新しい値は、30 秒ごとの定期的な処理で破棄します。次の同期で、新しい値を作り直します。トークンの有効期限が切れたことは、同じ処理で履歴（`token`）に残します。
- 値を導出で作るため、未使用の新しい値はハッシュだけを保存しつつ、エージェントが保存に失敗した場合に次の接続で同じ値を再び渡せます。
- 新しい値で最初に接続した時点で `hash` と `value` を置き換え、古い値を無効にします。それまでは古い値もその有効期限まで受け付けます。
- エージェントは新しい値を `agent.db` に 1 つのトランザクションで保存します。失敗したら古い値で接続を続けます。
- トークン名、インスタンス ID の結び付け、検知、適用中の監視ルールは agents 行と監視対象ごとの DB に結び付いているため、更新の前後で変わりません。

### 8.5 再発行と失効

- 再発行は新しい乱数の値と有効期限を設定し、`pending_hash` を消すため、それまでの値はすべて無効になります。失効も解除します。インスタンス ID の結び付けは維持します（別のエージェントにする場合は結び付けを解除する）。
- 失効は `revoked_at` を設定し、以後の接続を拒否します。
- エージェントの認証と同期がトークンに書き込むのは、その処理で変わる列（新しい値への切り替え、インスタンス ID の結び付け、使用の日時、自動更新の新しい値）だけです。書き込みは、読み取った時点から行が変わっておらず失効していない場合に限ります。そのため、ワーカー数が 2 以上で同時に処理しても、管理者の失効、再発行、結び付けの解除が取り消されることはありません（行が変わっていた要求は拒否し、自動更新の新しい値はその回は渡しません）。

## 9. auditd の扱い

### 9.1 生成するルール

監視ルールの値を次のひな形に当てはめて生成します。すべてのルールにキー `mimamori` を付けます。対象のアーキテクチャは x86_64 と arm64（aarch64）の 64 ビットだけで、実行ファイルをビルドしたアーキテクチャ（`runtime.GOARCH`）のルールを生成します。`exclude_interactive` が有効なら、実行、拒否された操作、読み込みのルールに `-F auid=4294967295` を加えます（通信のルールには加えません）。

| 種類 | ルール（ユーザーごと / 要素ごと） |
| --- | --- |
| 実行 | `-a always,exit -F arch=b64 -S execve -S execveat -F euid=<uid> -k mimamori`（x86_64 では 32 ビットのプログラムのため b32 も。arm64 では b64 だけ） |
| 拒否された操作 | `-a always,exit -F arch=b64 -S <ファイル操作の syscall> -F exit=-EACCES -F euid=<uid> -k mimamori`（`-EPERM` も。ファイル操作の syscall は、x86_64 では `open,openat,openat2,creat,truncate,unlink,unlinkat,rename,renameat,renameat2,mkdir,mkdirat,rmdir,chmod,fchmodat,chown,fchownat,lchown,link,linkat,symlink,symlinkat`、arm64 では aarch64 に存在するものだけの `openat,openat2,truncate,unlinkat,renameat,renameat2,mkdirat,fchmodat,fchownat,linkat,symlinkat`） |
| 読み込み | `-a always,exit -F arch=b64 -F dir=<dir> -F perm=r -F success=1 -F euid=<uid> -k mimamori` |
| 通信 | `-a always,exit -F arch=b64 -S connect -F exe=<path> -k mimamori` |

全体の設定: `-b 8192`、`-f 1`（障害時にホストを停止させない）、`--backlog_wait_time 0`（記録が溢れてもプロセスを待たせない）。

### 9.2 適用の手順

1. 監視ルールを検証する。失敗したら適用せず、前の監視ルールのまま動作してエラーを報告する。適用に失敗した版は確認のたびに再試行しない（再試行のたびに読み込み済みのルールを入れ替えて監視が途切れるため）。管理者が別の版を適用するか、エージェントを再起動すると再び適用する。動作中の版が改めて割り当てられた場合は、その版の成功した適用の結果を報告し直す
2. OS のユーザー、ディレクトリ、実行ファイルの存在を確認する。存在しない要素は除外し、`warn` の要素は注意として報告する。走査の起点が存在しない場合は、常に注意として報告する
3. ルールを生成する
4. `auditctl -s` で `enabled 2`（変更不可）なら失敗とする。このシステムのものが何も適用されていない（キー `mimamori` のルールが読み込まれておらず、ルールファイルも無い）ときは、手順 7 で変える全体の設定の値（`auditctl -s` の `backlog_limit`、`backlog_wait_time`、`failure`）を、何かを変える前にローカル DB（`state` の `audit_globals`）に記録する。記録が既にあれば残す（このシステムが変える前の値のため）。記録に失敗したら何も変えずに失敗とする。このシステムのものが既に適用されている（記録を持たない以前の版が適用した）場合は、その時点の値はこのシステムが設定したものなので記録しない
5. 次回の起動のため `/etc/audit/rules.d/zz-mimamori.rules` に全体の設定と生成したルールを書く。既存のファイルはその場で上書きし、`/etc/audit/rules.d` が無い場合は作らずに書かない（適用の結果に注意を付ける。エージェントは起動時に適用し直す）。`/etc/audit/rules.d` の他の `.rules` ファイルに `-a never,task`（`task,never`、`-A` も）がある場合は、ファイルの最後に `-d never,task` を書く（起動時に augenrules が名前の順に読み込むと、OS 標準の抑制ルールが先に読み込まれ、最後に打ち消されるため、再起動からエージェントの起動までの間も監査が抑制されない）。抑制ルールが他のファイルに無い場合は書かない（起動時に読み込まれない抑制ルールを打ち消す行は失敗し、`auditctl -R` はそこで読み込みを止めるため、augenrules が最後に置く `-e` の設定が読み込まれなくなる）。生成したルールが 0 件ならファイルを削除する（OS 標準のファイルは編集しない。augenrules は rules.d を C ロケールのファイル名の順に連結し、全体の設定は後の値が有効になる。番号の無い OS 標準のファイル（`audit.rules` など）よりも後に並ぶよう `zz-` で始まる名前にして、OS 標準の値を上書きする）
6. 読み込まれているルールのうち、キー `mimamori` のものだけを 1 件ずつ `auditctl -d` で削除する（他のルールに影響しない）
7. 全体の設定を `auditctl` で設定する
8. `-a never,task`（Amazon Linux 2023 などで、すべてのシステムコールの監査を抑制する既定のルール）が読み込まれていれば `auditctl -d never,task` で打ち消す
9. 生成したルールを読み込む
10. `auditctl -l` で件数と抑制ルールの無いこと、`auditctl -s` で `failure 1` と `backlog_wait_time 0` を確認する。いずれかの段階で失敗したら、キー `mimamori` のルール、全体の設定、手順 8 で打ち消した抑制ルール、ルールファイルを元に戻してエラーを報告する。適用の前にルールファイルが無かった場合はファイルを削除し、読めなかった場合（ディレクトリなど）は何も削除しない（新しい内容を書き込んでいれば、そのファイルは元に戻せなかったとエラーに示す）。元に戻す操作の一部が失敗した場合は、完全には戻せなかったことをエラーに示す

打ち消す前から動いているプロセスには監査が効かないため、導入の案内で、打ち消した後に監視対象のユーザーで動いているプロセスを再起動するよう案内します（プロセスの一覧は `/proc` を読まないため取得しません）。自ホストの情報では、抑制ルールが残っているかを報告します。

エージェント（内蔵エージェントを含む）を停止しても、読み込んだキー `mimamori` のルールと全体の設定、ルールファイルはそのまま残り、auditd は記録を続けます。次に起動したときに、保存している監視ルールを適用し直します。読み込んだルールを削除し、ルールファイルを削除するのは、生成したルールが 0 件の監視ルールを適用した場合（手順 5、6）、監視ルールの割り当てが無くなった場合（8.2）、無効にした内蔵エージェントに適用の記録が残っている場合（4.2）です。後の 2 つは、`auditctl -s` で `enabled 2` なら失敗とし、ルールファイルとキー `mimamori` のルールだけを削除して、残っていないことを `auditctl -l` で確かめます。このとき `/etc/audit/rules.d` の他の `.rules` ファイルに `-a never,task`（`task,never`、`-A` も）があり、その抑制ルールが読み込まれていなければ、`auditctl -a never,task` で読み込み直し、再起動を待たずに OS の設定どおりの状態に戻します。続けて、手順 4 で記録した全体の設定があれば、`auditctl -b`、`-f`、`--backlog_wait_time` で記録した値に戻し、記録を消します（再び適用するときに改めて記録します）。戻す操作の一部が失敗しても、ルールの削除は取り消さず、ほかの設定は戻し、削除の失敗と同じようにログと適用の結果（無効にした内蔵エージェントではログ）で報告し、記録を残して次の確認（内蔵エージェントでは次の起動）で再試行します。記録が無い場合（記録を持たない以前の版が適用した場合）は全体の設定を変えません（ルールファイルが無くなるため、次の起動からは OS 標準の設定に戻ります）。

### 9.3 記録の取得と集約

- 前回の続きの読み取りは、エージェントが最後に読んだイベントの位置（時刻の秒とミリ秒、通し番号）をローカル DB に保存して行います。`ausearch --input-logs --raw -k mimamori -ts <最後のイベントの秒>` で読み、すでに読んだイベントを除きます。`--input-logs` はローテーションした記録も読みます。初回は 10 分前から読みます。ausearch のチェックポイント機能は、版によって新しいイベントを返さないことがあるため使いません。
- ausearch は `LC_ALL=C`、`TZ=UTC` で実行し、`-ts` の日付は C ロケールの形式（`MM/DD/YY`）で渡します。日付の誤りなどで終了コード 1 と標準エラーにエラーを返した場合は、読み取りの失敗として扱います。
- SYSCALL、EXECVE、PATH、CWD、SOCKADDR の記録をイベントごとにまとめ、次の規則で種類を判定します。execve / execveat / connect は、記録の `arch` ごとの番号で判断します（x86_64 `c000003e`: 59 / 322 / 42、x86_64 上の 32 ビットのプログラム `40000003`: 11 / 358（connect は判定しない）、aarch64 `c00000b7`: 221 / 281 / 203。aarch64 の番号は audit パッケージの表（`ausyscall aarch64 execve` など）と `asm-generic/unistd.h` の値）: 成功した execve / execveat は実行、権限で拒否された（`-EACCES` / `-EPERM`）execve は拒否された操作、それ以外の失敗した execve（PATH の探索で見つからないなど）は除外、connect は通信（IPv4 / IPv6 の相手のみ。UNIX ソケットは除外）、失敗で `-EACCES` / `-EPERM` は拒否された操作、成功のそれ以外は読み込み。
- 「種類、OS のユーザー（euid の名前）、実行ファイル、対象（実行はコマンドライン、ファイルは CWD を考慮した絶対パス、通信は IP:ポート）」の組ごとに件数と最初と最後の発生時刻にまとめます。コマンドラインは引数 64 個までを使い、対象は 512 バイトまでに切ります。

## 10. ファイルの走査

- シンボリックリンクはたどらず（`WalkDir` と `Lstat`）、走査の起点と異なるファイルシステムのディレクトリには入りません。
- 1 回の確認でたどるのは、書き込み可能な状態の走査と実行されるファイルの走査のそれぞれで 2,000,000 項目（`MaxScanEntries`）までです。上限に達したら、次にたどるはずだった項目のパスを覚えて、次の確認でそこから続けます（`WalkDir` の順序、つまりパスをディレクトリ名ごとに比べた順で、その前の項目は数えずに飛ばし、上にあるディレクトリは報告せずに中に入る）。最後までたどったら 1 巡の終わりで、次の 1 巡は先頭から始めます。途中で止めたこと、続けたこと、1 巡を終えたことはエージェントのログに出し、続きを回している間は自ホストの情報（11 章、[API仕様.md](API仕様.md) の `incomplete_scans`）でセントラルに知らせます。
- 書き込み可能な状態の走査は、1 巡の途中なら間隔にかかわらず毎回の確認で続けます。報告済みの組の整理（見つからなくなった組を忘れる）と書き込みを許可するパスのディレクトリの置き換えは、1 巡を終えたときに、その 1 巡を始めた時刻で行います（途中では前の 1 巡のディレクトリに見つけたものを加える）。次の 1 巡は、終えた 1 巡を始めた時刻から間隔が過ぎたら始めます。
- 実行されるファイルの走査は、走査の順序の区間ごとに最後に確認した時刻を持ちます。1 回の確認でたどった区間（続きの始まりから止まった所まで）はその確認の開始の 1 秒前を、まだたどっていない区間はその区間を前回たどった時刻を使うため、どの部分も最後に確認した時刻より新しいファイルだけを対象にし、取りこぼしも二重の報告もありません。走査の間に増えたファイルや移動したファイルは、状態の変更時刻が新しくなるため、その部分を次にたどるときに見つかります。続きの始まりのパスが無くなっていても、順序で位置を決めるため続きから始まります。
- 書き込みを許可するパスと正当な配置場所は、走査の起点からの相対パスの途中の連続したディレクトリ名として判定します（`storage` は `/opt/a/storage`、`/opt/a/prod/storage`、`/opt/x/a/prod/storage` のいずれにも一致）。
- 書き込み可能な状態（`scan_interval_sec` ごと）: 書き込みを許可するパスに一致するディレクトリは記録して中に入らず、それ以外で、監視ルールの OS のユーザーが所有する、またはグループかその他に書き込み権限があるファイルとディレクトリを検知します。報告済みの（パス、状態の変更時刻、所有者、権限）の組は再報告しません。
- 実行されるファイル（毎回）: 最後の全体の走査で見つけた書き込みを許可するパスのディレクトリだけをたどり、指定した拡張子で、状態の変更時刻（ctime。所有者が偽装できる更新時刻は使わない）が前回の確認より新しいファイルを検知します。全体の走査で新しく見つかった書き込みを許可するパスのディレクトリは、前回の全体の走査（最後に終えた 1 巡を始めた時刻の 1 秒前）より新しいファイルを対象にします（ディレクトリが書き込みを許可するパスとして見つかる前に作られたファイルも検知するため）。この時刻は、実行されるファイルの走査がそのディレクトリを最後までたどるまで保ちます（全体の走査が見つけた回と、実行されるファイルの走査がそこに届く回が違ってもよいように）。走査の起点や書き込みを許可するパスを変えた後の最初の全体の走査では、それまで対象でなかったディレクトリを初回と同じ扱いにし、既にあるファイルも対象にします。それまでも対象だったディレクトリは、前回の確認より新しいファイルだけを対象にします。変更の時点で途中だった書き込み可能な状態の走査の 1 巡は捨てて先頭から始め、それまでのディレクトリは変更後の最初の 1 巡を終えるまで残します（実行されるファイルの走査は、走査の起点の中にあるディレクトリだけをたどる）。正当な配置場所の中で拡張子も一致すればその分類、それ以外は `other_category` です。初回の走査では、既存のファイルのうち正当な配置場所のものは報告せず、報告済みと同じように記録して、次の確認でも報告しません。

## 11. 自ホストの情報

OS の名前とバージョン（`/etc/os-release`）、ホスト名、カーネル（`uname` システムコール）、auditd の状態（`auditctl -s` の値、取りこぼしの件数、抑制ルールの有無、ホストを停止させる設定）、適用中の監視ルールの走査の起点の配下 3 階層までのディレクトリ（300 件まで）、エージェントのバージョン、適用中の監視ルールと版、最後の適用の結果、信頼している独自 CA、項目数の上限に達して続きを次の確認に回しているファイルの走査（種類、続きを始めるパス、上限、その 1 巡を始めた日時。10 章）、エージェントの実行ユーザー（実効 UID の名前。コマンドセットの OS のユーザーの既定値）、ホストのタイムゾーン（略称と UTC からのずれ。定期のコマンドセットの時刻の解釈に使う）。`/proc` と `/etc/machine-id` は読みません。そのため、要件にある「動いている Web サーバーと php-fpm のプロセスと実行ユーザー」と「抑制ルールの影響を受けているプロセス」は報告しません。

なお、`/proc` は mimamori のコードからは読みませんが、Go の実行環境（`/proc/self/cgroup`、`/proc/self/mountinfo`）、SQLite ドライバー（`/proc/self/exe`、`/proc/self/maps`）、`auditctl` などの auditd の道具は、それぞれ自身の処理で読みます。

## 12. セントラルの機能

### 12.1 検知の保存

- 報告の検知は、その監視対象の DB に保存します。同じ fingerprint の未確認の行があれば件数と時刻をまとめ、無ければ新しい行を作ります。確認済みにした後の発生は新しい行になります。
- 抑止条件に一致した検知は `suppressed = 1` で記録し、通知しません。抑止条件を作成した時点で、一致する未確認の検知にも反映します。
- 抑止条件を削除すると、その条件で抑止していた未確認の検知は抑止されていない状態（`suppressed = 0`、`suppression_id = 0`）に戻り、通知待ちの検知として扱います（通知の対象外だった検知は、同じ検知を重複抑止の期間内に通知していなければ通知待ちになります。同じ検知に新しい発生を集約するときと同じ規則です）。残っている別の抑止条件に一致する検知は、その条件で抑止したままにします。確認済みの検知は変えません。戻した件数は削除の履歴に残します（`core.releaseSuppression`）。
- 保存期間（既定 180 日）を過ぎた検知は 1 時間ごとに削除します。拒否した接続の履歴も同じ期間で削除します。同じ処理で、期限切れのセッション、確認コード、確認済みのブラウザと、送信から 30 日を過ぎた通知メール、保存期間を過ぎたコマンドセットの実行と終わった指示（12.5.8）も削除します。

### 12.2 通知

- 30 秒ごとの定期的な処理で、未送信のメールが無く、前回の送信から最小間隔（既定 30 分）を過ぎていて、通知待ちの検知があればメールを 1 通作成します。最小間隔の間に増えた検知は次の 1 通にまとめます。
- 新しい検知は通知待ちになります。同じ fingerprint を設定の期間（既定 24 時間）以内に通知していれば通知しません。期間を過ぎて同じ検知が再び発生したら通知します。
- 件名: `alert` を含む場合は `[mimamori] [ALERT] N alert(s), M new detection(s)`、含まない場合は `[mimamori] M new detection(s)`。
- 本文: エージェント（トークン名、または `(central)`）とホスト名ごとに、`alert`、`normal` の順（同じ分類の中は新しい順）で 1 検知 1 行（分類、種類、ユーザー、実行ファイル、対象、権限、所有者、件数、最後の時刻）。上限（既定 200 行）を超えた分は件数だけを示します。
- 作成したメールは `notifications` に保存し、送信できるまで定期的な処理のたびに再送します。未送信のメールが残っている間は新しいメールを作成せず、その間の検知は次の 1 通にまとめます。そのため、送信できない期間が続いても、復旧後に複数のメールを続けて送ることはありません。
- 宛先: 全ユーザーや全管理者ではなく、管理者が通知先として 1 人ずつ選んだアカウントです。アカウントごとの「通知メールを受け取る」の選択（`accounts.notify`、既定はオフ。権限に関係なく選べる）がオンで、無効化されていないアカウントのメールアドレスだけです（`models.ListNotifyEmails`）。アカウントでない固定のアドレスを宛先に加える設定はありません。以前の版で保存した設定 `smtp.to` は読み込み時に無視し（エラーにしない）、`central config set smtp.to ...` は他の存在しない名前と同じく失敗します。選択は、システム設定の画面の通知の「通知先」、`PUT /accounts/{id}/notify`（[API仕様.md](API仕様.md) の「アカウント」）、`ctl accounts notify` で変えます。無効化したアカウントは選択を保ったまま、無効の間だけ宛先から外れます。
- 送るのは、`smtp.host` と `smtp.from` がそろっていて（`SMTPConfig.CanSend`）、宛先が 1 つ以上ある場合だけです。宛先は送信のたびに求めるため、未送信のメールは送る時点の宛先へ送ります。宛先が無い間は、メールを作成も送信もせず（エラーにもしない）、検知は通知待ちのまま残り、宛先ができた後の 1 通にまとめます。送信の関数は確認コードと同じ `core.sendMail` です。
- 確認コード（ログイン、メールアドレスの変更、コマンドセットの変更の再認証）のメールは通知ではなく、この選択に関係なく、対象のアカウントのアドレスへ送ります（12.4）。

### 12.3 独自 CA とサーバー証明書

- 初回起動時に独自 CA（ECDSA P-256、5 年）とサーバー証明書（397 日、`server_names` とループバック）を作成します。
- サーバー証明書は、残り 30 日を下回った、名前の設定が変わった、署名した CA が現在の CA でない場合に作り直し、再起動せずに切り替えます（`GetCertificate`）。
- CA の切り替え: 独自 CA の残りが 180 日を下回ったら新しい CA（`next`）を作ります。同期の応答で、エージェントが持っていない CA を配布します。エージェントは新旧の両方を信頼します。30 日後に新しい CA を `active` にし、古い CA を `retired`（期限まで信頼）にして、新しい CA で署名したサーバー証明書に切り替えます。期限切れの CA は破棄します。
- 新しい CA をまだ受け取っていないエージェント（同期で送られたフィンガープリントに現在の CA が無い）を画面に表示します。一度も同期していない（接続したことのない）エージェントは、まだ CA を報告していないため対象にしません。エージェントの一覧と詳細、証明書の画面、`ctl certs status` は同じ判定です。CA の切り替えに間に合わなかったエージェントは初期化し直して復旧します。
- 証明書と秘密鍵は central.db（0600）に保存します。CLI 用に公開の CA 証明書を `ca.crt` に書きます。

### 12.4 アカウントと認証

- パスワードのハッシュ（方式と形式は [テーブル定義.md](テーブル定義.md) の `accounts`）は 600,000 回、16 バイトの salt で作ります（長さの条件は [API仕様.md](API仕様.md) の「アカウント」）。
- アカウントの項目は、ログイン ID のメールアドレス、パスワード、表示名、権限、表示言語、通知メールを受け取るかどうか（12.2）です（列は [テーブル定義.md](テーブル定義.md) の `accounts`、値の条件は [API仕様.md](API仕様.md) の「アカウント」）。メールアドレスと表示名の検証は `app/modules/account_validate.go` の `ValidateEmail` / `ValidateDisplayName` だけで行い、ブラウザ用の API、`ctl`、`central init-admin` が同じ関数を使います。
- ログインはメールアドレス（大文字と小文字を区別しない）とパスワードで行い、開発モード（下記）以外では、続けてメールで届く確認コードを入力する 2 段階で行います（要求と応答は [API仕様.md](API仕様.md) の 2 章）。
  - パスワードが正しい場合、次のどれかになります。開発モードではコードを求めずにログインします（履歴の詳細に `two-step verification skipped (SMTP not configured)`）。確認済みのブラウザ（下記）からはコードを求めずにログインします（`verified browser`）。それ以外では、確認コード（`AuthCodeDigits` 桁の数字）をアカウントのメールアドレスへ送り、`202` で challenge を返します。コードの桁数、有効期限、誤りの上限、再送が無いことは [API仕様.md](API仕様.md) の 2 章のとおりです。
  - 有効期限は `AuthCodeLifetime`、誤りの上限は `AuthCodeMaxAttempts` です。コードは保存せず、サーバーの鍵による HMAC-SHA256（`modules.HashAuthCode`。目的、アカウント、challenge またはセッションに結び付ける）だけを `auth_codes.code_hash` に保存します。challenge はランダムな値（接頭辞 `mmk_`）で、ハッシュ（`challenge_hash`）だけを保存します。パスワードの入力からやり直すと、そのアカウントの古いログインのコードは削除され、新しいコードに置き換わります。正しいコードは 1 つの SQL 文（`models.ConsumeAuthCode`。誤りが上限に達していない、期限内の行だけを削除する）で使用済みにするため、同時の要求でも 1 つのコードで成功するのは 1 回だけで、誤りの上限を超えて試すこともできません。
  - コードの誤りは、パスワードの誤りと同じ失敗の回数（`models.RecordLoginFailure`）に数え、5 回で 15 分ロックします。失敗の回数は、ログインが完了した時点で 0 に戻します（コードを求める場合、パスワードが正しいだけでは戻さない）。
  - 正しいコードでログインし、セッションを作ります。「ログインを保持する」は、パスワードの段階での選択（`auth_codes.remember`）を使います。履歴の詳細は `code verified`、信頼を選んだ場合は `code verified, browser trusted` です。
- 確認済みのブラウザ: コードを入力したブラウザに Cookie `mimamori_verify`（属性は [API仕様.md](API仕様.md) の 2 章。値は接頭辞 `mmv_` のランダムな値）を発行し、そのハッシュを `browser_verifications` に保存します。同じブラウザの古い行は削除します。
  - 「N 日間このブラウザを信頼する」（N は `two_step_trust_days`）を選んだ場合は、コードの入力から N 日の間（現在の設定の N で判定）、同じアカウントのログインでコードを省きます。行は最長の 365 日（`MaxTrustDays`）まで残すため、N を長くすると既存の信頼にも反映します。
  - 選ばなかった場合は、コードの入力から 3 時間（固定。使っても延びない）の間、同じブラウザからの同じアカウントのログインでコードを省きます。3 時間は設定項目ではなく、定数 `VerifiedBrowserTTL` です。ログイン中のセッションは 3 時間では切れません（セッションは操作なしの 1 時間だけで失効する）。
  - Cookie の `Max-Age` は、信頼するかどうかに関係なく同じです。行が有効かどうかはサーバーだけが判定するため、3 時間はブラウザに現れません（1 時間と同じく、画面、API の応答、Cookie の属性、設定、履歴、README、CHANGELOG のどれにも出さない）。
  - ほかのアカウントの行、期限を過ぎた行では省きません。ログアウトでは削除しません。
- ログインに 5 回続けて失敗すると、そのアカウントは 15 分間ログインできません。失敗の回数とロックは 1 つの SQL 文で更新するため、同時に失敗しても回数は失われず、ロックが解除されることもありません。存在しないメールアドレスでも同じ時間がかかるように、ダミーのハッシュを検証します。
- セッションは Cookie（名前は [API仕様.md](API仕様.md) の 1.1、保存の形式は [テーブル定義.md](テーブル定義.md) の `sessions`）で、HttpOnly、SameSite=Strict です。ブラウザに保存するのはこの Cookie だけです（localStorage などは使わない）。
- 通常のセッションは有効期限の無い Cookie（ブラウザを閉じると消える）で、最後の操作から 1 時間で失効します。1 時間は設定項目ではなく、`app/modules/constants.go` の定数 `SessionIdleTimeout` です。ブラウザの利用者には示しません（画面、API の応答、Cookie の属性、設定、履歴、README、CHANGELOG のどれにも出さない）。
  - 操作とは、ブラウザ用の API への要求のうち、ヘッダー `X-Mimamori-Background: 1` が無いものです。開いている画面の定期的な更新（概要の 60 秒ごとの取得）はこのヘッダーを付けるため、画面を開いたままにしてもセッションは延びません。ヘッダー付きの要求も認証はします。
  - 延長は、前回の延長から 60 秒を過ぎた操作で、有効期限を「その時刻 + 1 時間」に書き換えて行います。
- ログイン画面で「ログインを保持する」を選ぶと、Cookie に `session_remember_days`（既定 30 日）の有効期限を付け、セッションもログインから同じ期間で失効します（操作による延長はしない）。CSRF 対策のヘッダーは [API仕様.md](API仕様.md) の 1.2 のとおりです。
- 開発モードは `smtp.host` が空（前後の空白を除いて）の状態です（`SMTPConfig.DevelopmentMode`）。メールを送れないため、通知を送らず、確認コードも求めません。確認コードのメールは、`smtp.host` と `smtp.from` がそろっている場合（`SMTPConfig.CanSend`）に、`modules.SendMailTo` で指定した宛先へ送ります。通知メールは、これに加えて宛先が 1 つ以上ある場合に、12.2 の宛先へ送ります。
- 確認コードのメールは、要求を処理する中で同期して送ります（メインループは変えない）。送信の関数は `core.sendMail`（既定は `modules.SendMailTo`。テストで差し替える）で、時間の制限は `smtp.timeout_sec` と 45 秒（`AuthCodeMailTimeoutCap`。応答を接続全体の制限 60 秒以内に書くため）の短いほうです。送信中は、`workers` が 1 の場合、ほかの要求は待ちます。
  - メールは英語で、件名は `<notify.subject_prefix> Verification code`、本文はコード、用途（`login` / `e-mail address change` / `re-authentication for changes to command sets`）、有効期限 10 分、要求元の IP アドレス、時刻（UTC）です。
  - `smtp.host` が設定されていて送れない場合（`smtp.from` が空、接続、認証、宛先の拒否、時間切れなど）は、ログインを `503` で失敗にし、履歴に `login_code_failed`（詳細に SMTP のエラー）を残します。セッションもコードも作りません。
- メールを送れずにログインできない場合の復旧は CLI で行います（手順は [CommandReference-ja.md](CommandReference-ja.md) の `central`。ブラウザの利用者には CLI を案内しない）。
- 本人による変更（プロファイルの画面）:
  - 表示名は即時に変更し、何も無効にしません。
  - メールアドレスは、新しいアドレスだけを入力します（現在のパスワードは求めない）。新しいアドレスへ確認コードを送り、そのコードを、依頼したのと同じセッションで正しく入力した時点で変更します。コードの条件（有効期限、誤りの上限、ハッシュだけを保存）はログインと同じですが、誤りはログインの失敗の回数に数えず、`400` で返します（`401` はブラウザがログアウトとして扱うため）。5 回誤ると依頼を破棄し、やり直しになります。新しい依頼は、確定していない古い依頼を置き換えます。送れない場合は `503` で、履歴に `email_code_failed` を残します。
  - 開発モードでは、メールアドレスもコードなしで即時に変更します。
  - 履歴は `display_name_changed` / `email_changed`（詳細の末尾に `(own change)`）です。
- アカウントの変更の時点で、次のものを無効にします（`modules.RevokeAccountAuth` がセッション、確認済みのブラウザ（`browser_verifications`）、送信済みの確認コード（`auth_codes`）をまとめて削除し、残したセッションの再認証（12.5.10）も消す）。期限を過ぎた確認コードと確認済みのブラウザは、1 時間ごとの保存期間の処理で削除します。

  | 変更 | セッション | 確認済みのブラウザ | 確認コード |
  | --- | --- | --- | --- |
  | 自分のパスワードの変更 | 操作したセッション以外 | すべて | すべて |
  | 管理者、`ctl`、`central reset-password` によるパスワードの変更 | すべて | すべて | すべて |
  | 本人によるメールアドレスの変更（確定、または開発モードでの即時の変更） | 操作したセッション以外 | すべて | すべて |
  | 管理者、`ctl` によるメールアドレスの変更 | すべて | すべて | すべて |
  | 無効化 | すべて | すべて | すべて |
  | 権限の変更 | すべて | 変えない | 変えない |
  | 表示名の変更 | 変えない | 変えない | 変えない |
  | 削除 | 連鎖削除 | 連鎖削除 | 連鎖削除 |

- 管理者（ユーザー管理の画面と `ctl accounts email` / `display-name` / `password`）は、どのアカウントのメールアドレス、表示名、パスワードも確認コードなしで即時に変更できます。自分のアカウントも同じです。
- 権限の判定はすべての API でセントラルが行います（`requireAny` / `requireAdmin`）。管理用の API の接続元と認証は [API仕様.md](API仕様.md) の 1.1 のとおりです。
- 操作の履歴（`history.account_name`）と、各表の `created_by`、`acknowledged_by` には、操作したアカウントのその時点のメールアドレスを記録します（CLI の操作は 5 章のとおり。定期的な処理などシステムの処理は `system`）。メールアドレスを変えても、記録済みの行は書き換えません。閲覧者への応答では、記録した値を表示名に変換して返します（変換の規則は [API仕様.md](API仕様.md) の 1.3。実装は `operatorShown` の 1 か所）。閲覧者には、アカウント、システム設定、コマンドセットの履歴を返しません（[API仕様.md](API仕様.md) の 11 章）。画面の履歴の分類の選択肢にも出しません。
- ブラウザ用の待ち受けの応答には `X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`、`Content-Security-Policy`（`default-src 'self'`、`frame-ancestors 'none'` など）を付けます。

### 12.5 コマンドセット

監視対象のホストで、エージェント（内蔵エージェントを含む）が、定義したコマンドを指定した OS のユーザーとして、手動の指示または定期で実行し、コンソール出力を記録してセントラルに報告する機能です。要求と応答、項目の値の範囲と既定値は [API仕様.md](API仕様.md) の 4.1 章と 14 章、テーブルは [テーブル定義.md](テーブル定義.md)、CLI は [CommandReference-ja.md](CommandReference-ja.md) の `ctl command-sets` を参照してください。

#### 12.5.1 定義と保存場所

- 定義は監視対象ごとに持ち、その監視対象の DB（`command_sets`、`command_items`）に保存します。監視対象をまたいだ定義の一覧や設定はありません。監視対象をまたいで見られるのは、出力収集のセットの結果（同じ名前のセットを並べる）だけです。
- セットは、名前（その監視対象の削除されていないセットの中で一意）、説明、用途（出力収集 `collect_output` / 実行のみ `run_only`）、OS のユーザー、作業ディレクトリ、実行方法（手動 / 定期）とスケジュール、保存する実行の回数、値のつなぎ方（カンマ / 改行）と、順序付きのコマンドから成ります。コマンドは、コマンドライン、備考、成功と失敗の戻り値の指定、問題があったときの動作、制限時間、行数の上限、正規表現の並びを持ちます。コマンドには名前も同一性も無く、同じコマンドラインを何度でも並べられます。セットを保存するたびにコマンドの行はすべて入れ替えます。
- セットは保存のたびに版（`revision`）が増え、削除は論理削除です（実行の結果は保存期間まで残る）。
- 検証は保存時にセントラルで行い（`modules.CommandSetSpec.Validate`）、エージェントでも受け取ったときにもう一度行います（正規表現のコンパイルを含む）。コマンドラインの中身は検査しません（空、NUL を含む、102400 バイトを超える、の 3 つだけを拒否します）。
- 配信: エージェントは同期のたびに、保持している定義の署名を送ります。署名は、監視対象の DB を作ったときの乱数（`db_instance`）と、削除されていないセットの ID と版から作る SHA-256 です。セントラルは署名が現在の定義と違えば、すべての定義を同期の応答で送ります。DB を作り直すと乱数が変わるので、セットの ID と版が偶然同じでもエージェントは定義を受け取り直します。エージェントは定義を状態 `command_defs` に保存し、受け取った結果（検証に失敗したセットとその理由）を報告します。セントラルはそれを `agents.command_problems` に保存し、署名が現在の定義と一致する間だけ管理者に表示します。
- インポートは、ほかの監視対象または同じ監視対象のセットを、OS のユーザーと作業ディレクトリを含めてすべて写します。セットごとに名前を変えられます。写し先の名前、またはインポートの中で名前が重なると、何も作らずに重なった名前を返します。

#### 12.5.2 エージェントでの実行

実装は `app/modules/cmdexec.go`（1 つのコマンドの実行）と `app/modules/agent_commands.go`（定義と指示の受け取り、実行の順番、実行の記録と報告）です。

- 処理の流れ: エージェントは 1 つの流れのまま実行します（4.1）。コマンドの終了を待つループの中で、確認の間隔が過ぎるたびに監視の処理（同期、auditd の記録の取得、走査、報告）を行い、その前後でパイプを読みます。同期で受け取った定義と指示は保存だけして、実行中のセットは開始したときの定義で最後まで動きます。
- 実行の順番: 1 度に 1 セットだけ実行します。手動の指示（指示の古い順）を先に、次に予定の来た定期のセット（予定の古い順）を実行します。
- 同じ実行を 2 回行わない: 実行ごとに一意な ID を作り、開始と終了をエージェントのローカル DB の `command_executions` に記録します（手動の指示の ID はここで一意）。定期の予定は、実行の前に実行済みとして記録します。起動時に終了していない実行は、中断（`error`、理由 `interrupted`）として報告します。実行中のコマンドの位置と開始日時もコマンドを始める前に記録し、その結果を未送信の報告に入れた後に消します。起動時に記録が残っていれば、そのコマンドの結果（`error`、理由 `interrupted`、記録した開始日時、終了日時は起動時、戻り値なし、出力は空。コマンドラインと備考は、保存している定義の版が実行の版と同じときだけ）も報告します。その位置の結果をセントラルがすでに受け取っていれば、最初の結果が残ります。エージェント自体が異常終了したとき（例えば強制終了されたとき）、実行中のコマンドはエージェントによっては終了されず、その実行は次の起動時に中断として報告されます。終了した記録は 2 日後に消します（指示の期限より長い）。
- OS のユーザーの既定値: エージェントは自ホストの情報（11 章）で自身の実行ユーザーを報告し、セントラルは監視対象ごとに保存します。これが新しいセットの OS のユーザーの既定値です（画面の初期値、API と CLI で省略したとき）。作成のときにも後からでも変えられます。一度も接続していない監視対象には既定値がありません。
- 起動の方法: セットの OS のユーザーがエージェントの実行ユーザーと同じ（名前が `/etc/passwd` で解決できれば UID で、できなければ名前で比べる）なら `bash -c <ラッパー> ...` を直接起動し、違えば `sudo -n -H -u <OS のユーザー> -- <bash の絶対パス> -c <ラッパー> ...` で起動します。`sudo` と `bash` は `PATH` から探します。`-n` によりパスワードは求めず、求められる設定なら起動の失敗になります。標準入力は `/dev/null`、標準出力と標準エラーは 1 本のパイプ（1 つのコンソール出力）、環境はエージェントの環境のまま（ロケールやタイムゾーンを置き換えない）です。新しいセッション（プロセスグループ）で起動するため、端末を持ちません。
- 別のユーザーで実行する設定: root で動くエージェントは、多くのディストリビューションの標準の sudoers（`root ALL=(ALL:ALL) ALL`）のままで、どのユーザーとしても実行できます。root 以外で動くエージェントには、選んだ OS のユーザーとして bash をパスワードなしで実行できる sudoers の設定が要ります。例（エージェントが OS のユーザー `mimamori` で動き、`app` と `deploy` として実行する場合。`visudo -f /etc/sudoers.d/mimamori` で作る）:

  ```text
  mimamori ALL=(app,deploy) NOPASSWD: /usr/bin/bash
  ```

  bash のパスは、エージェントの `PATH` で見つかるものと同じにします。`Defaults requiretty` が有効な環境では、端末を持たないため起動の失敗になります。この例は、エージェントに指定したユーザーとしての任意のコマンドの実行を許します。
- ラッパー: 固定の小さな bash のスクリプトで、乱数の印、作業ディレクトリ、コマンドラインを引数で受け取ります。印の行を出力し、作業ディレクトリに移り（`cd -- "$dir"`。作業ディレクトリが無いときは引数なしの `cd` でホームへ）、もう一度印の行を出力してから `exec "$BASH" -c "<コマンドライン>"` します。エージェントは出力の先頭の 2 つの印の行を取り除きます。1 つ目の印が無ければ起動の失敗（`start_failed`。sudo のメッセージなどの出力は残す）、2 つ目が無ければ作業ディレクトリに移れなかった（`workdir_failed`）とします。sudo は自身の失敗を終了コード 1 で返し、コマンド自身の終了コード 1 と区別できないため、戻り値ではなく印で判定します。
- 作業ディレクトリ: セットの作業ディレクトリ（空ならその OS のユーザーのホーム。sudo では `-H` で HOME もそのユーザーのものになる）で、どのコマンドも始まります。直接起動で作業ディレクトリが空のときは、`/etc/passwd` にあるエージェントの実行ユーザーのホームをラッパーに作業ディレクトリとして渡します。サービスは環境変数 `HOME` なしで起動されることがあり、そのとき引数なしの `cd` は失敗するためです。環境（`HOME` を含む）は変えません。`/etc/passwd` にそのユーザーが無いか、ホームが空なら、引数なしの `cd` のままです。コマンドラインは内側の `bash -c` に 1 つの引数としてそのまま渡るので、コマンドの中の `cd`、パイプ、リダイレクト、複数行はそのコマンドの中でだけ効き、次のコマンドはまたセットの作業ディレクトリから始まります。
- 制限時間と停止: 制限時間を過ぎたとき、またはエージェントの停止の指示があったときは、プロセスグループに `SIGTERM` を送り、10 秒後にまだ終わっていなければ `SIGKILL` を送ります。それまでの出力は残します。停止で終わったコマンドは `interrupted` とし、残りのコマンドは実行せず、その実行を未送信の報告に入れ、終了する前に 1 回だけ送信を試みます（送れなかった分は次の起動の後に送ります）。root 以外で動くエージェントは、sudo で別のユーザーとして起動したコマンドのプロセスグループにシグナルを送れない（sudo は root で動き、コマンドのプロセスはそのユーザーのもの）ため、拒否されたときは同じ sudoers の設定で `sudo -n -u <OS のユーザー> -- <bash> -c 'kill -s <シグナル> -- -"$1"'` を実行し、そのユーザーとして同じシグナルを送ります（最大 5 秒待ちます）。これも失敗して停止の指示があるときは、`SIGKILL` からさらに 10 秒待った後、コマンドの終了を待たずにその結果（`interrupted` または `timeout`）を記録し、終了できなかったことをエージェントのログに書きます（停止が止まらないようにするため）。正常に終わったコマンドがバックグラウンドに残したプロセスは終了させません（プロセスグループを終了させるのは制限時間と停止だけです）。
- 報告: 実行の開始、終わったコマンドごとに 1 件（最後の 1 件が実行の終了、状態、表示用の値を運ぶ）を未送信の報告に入れ、次の報告で送ります。どの報告にも開始時の値を含めるので、セントラルはどの報告からでも実行を作れます。未送信のコマンドセットの報告は合計 64 MiB までとし、超えたら古い順に、実行のみのセットの出力、出力収集のセットの出力（値は残す）、実行を閉じない報告、実行を閉じる報告の順に捨てます。
- コマンドセットの実行による操作（起動する外部コマンドを含む）も、ほかの操作と同じく監視の対象です（検知から除外しません）。

#### 12.5.3 結果の区分と「問題があったとき」

- 1 つのコマンドの結果は 3 つの区分のどれかです。`success` は戻り値が成功の指定にある、`failure` は失敗の指定にある、`error` はそれ以外のすべてです。`error` の理由（`reason`）は、どちらの指定にも無い戻り値（`unexpected_code`）、起動の失敗（`start_failed`）、作業ディレクトリの失敗（`workdir_failed`）、制限時間の超過（`timeout`）、シグナルによる終了（`signaled`）、エージェントの停止（`interrupted`）です。成功と失敗の指定は重ねられません（保存時のエラー）。
- 問題があったとき（コマンドごと）: `stop`（既定。失敗またはエラーでセットを止める）、`continue_on_failure`（失敗なら続け、エラーなら止める）、`continue_always`（どの場合も続ける）。止まった後のコマンドは「実行しなかった」として数え、4 つ目の区分にはしません。
- 実行の状態は、実行したコマンドの最も悪い区分です（`error` が `failure` より、`failure` が `success` より悪い）。

#### 12.5.4 定期

- cron の書式は使わず、種類（日時を指定した 1 回、毎週（曜日と時刻）、毎日（時刻）、n 時間ごと、n 分ごと、毎時 n 分）と値を選んで指定します。n の選択肢は [API仕様.md](API仕様.md) の 4.1 章のとおり、24 と 60 の約数で、0 時と 0 分から数えます。
- 日時を指定した 1 回は、画面ではブラウザのローカル時刻、CLI の定義ファイルでは CLI のローカル時刻（オフセットを省略した場合）で入力し、絶対時刻として保存します。過去の日時は保存時のエラーです（変更で保存済みと同じ日時のままなら可）。
- 繰り返しの種類は、crond と同じく監視対象のホストのローカル時刻で解釈します。エージェントはタイムゾーン（略称と UTC からのずれ）を報告し、画面と CLI はスケジュールの要約にそれを添えます。夏時間の切り替えでは、毎週と毎日の時刻が存在しなければ後ろへずらし（02:30 は 03:30）、2 回ある時刻は最初の 1 回だけ実行します。n 時間ごと、n 分ごと、毎時 n 分は時計の表示で判定するため、飛ばされた時間には予定が無く、繰り返す時間には 2 回あります。
- エージェントは、そのスケジュールの定義を最初に見た時刻（`command_schedules.armed_at`。スケジュールを変えると見直す）と、実行済みの最後の予定（`last_due`）の両方より後の最新の予定があれば実行します。作ったばかりのセットの過去の予定は実行しません。停止中や他のセットの実行中に過ぎた予定は、いくつあっても最新の 1 回だけ、気付いたときに実行します。予定の日時と実際の開始日時の両方を記録します。
- 定期のセットも手動で実行できます。

#### 12.5.5 手動の実行指示

- 管理者が指示を出すと、次の同期でエージェントに届きます（即時性はありません）。1 つのセットに、応答の無い指示（未配信 `pending` または配信済み `delivered`）は 1 つだけで、重ねた指示は拒否します。
- 24 時間以内に配信されなかった指示は期限切れ（`expired`）にし、履歴に残します（30 秒ごとの定期的な処理）。未配信の間は破棄できます。セットを削除すると、未配信の指示は破棄します。
- 配信済みの指示は、エージェントが応答するまで同期のたびに送り直します。エージェントは指示の ID で重複を除くため、同じ指示を 2 回実行しません（実行済みなら同じ実行の ID を応答します）。期限を過ぎてから届いた指示と、エージェントが持っていない（または検証に失敗した）セットの指示は実行せず、期限切れとして閉じます。

#### 12.5.6 表示用の値と正規表現（出力収集）

- コンソール出力と表示用の値は別のものです。コンソール出力は実行の履歴でいつでも見られ（1 MiB まで）、表示用の値は結果の画面に表示します。
- 正規表現が無いコマンド: コンソール出力の先頭から行数の上限までの行（実際の改行で数える。画面の折り返しは行ではない）が値です。
- 正規表現があるコマンド: コマンドの結果（成功、失敗、エラー）に関係なく、定義の順にそれぞれの正規表現をコンソール出力の全体に当て、すべての一致を出力の順に使います。値は名前付きグループ（`(?P<name>...)` または `(?<name>...)`）が取り込んだ文字列だけで、名前付きグループの外の一致部分は値ではありません。参加しなかった、または空のグループは値を出しません。何も取り出せなければ、そのコマンドは何も加えません。ただし、コマンドラインが起動しなかった場合（`start_failed`、`workdir_failed`）は、出力が起動や作業ディレクトリの移動のエラーメッセージなので値を取り出しません。
- 正規表現はエディタやスクリプト言語と同じ種類（`github.com/dlclark/regexp2`、オプション `RE2 | Multiline`）です。先読み、後読み、後方参照が使え、`\r` や `\n` を書けて、一致は行をまたげます。`^` と `$` は行の区切りでも一致し、`.` は `(?s)` を書かない限り改行に一致しません。名前付きグループの無い正規表現は保存時のエラーです。悪い正規表現でエージェントが止まらないよう、1 つのコマンドにつき正規表現ごとに 2 秒の制限があり、超えた正規表現は値を出さず、そのことを記録します。
- グループの番号は Python やエディタと同じく、名前の有無にかかわらず取り込むグループすべてを開き括弧の順に数え、`\1` などの番号の後方参照と `(?(1)...)` の条件はこの番号を使います。`(?P=name)` は `\k<name>` と同じ意味です。この番号付けを保証できない正規表現（まだ閉じていないグループや前に無いグループへの番号の参照、無いグループの番号の条件、名前の重複と番号の参照の併用、オプション `n`、番号を付けたグループ `(?<1>...)`、バックスラッシュで終わるコメント（Python はその続きもコメントとして読む）など）は保存時のエラーで、エージェントでは問題（`invalid`）として記録し、値を出しません（実装は `app/modules/cmdpattern.go`: 名前の無いグループにパターンに現れない名前を付けてからコンパイルし、コンパイル結果のグループが走査と一致することを確かめます）。
- このライブラリは `\Q...\E` による引用を実装せず `\Q` と `\E` を文字 Q と E として読むため、文字クラスの中も含めてエスケープ `\Q` または `\E` を含む正規表現は保存時のエラーで、エージェントでは問題（`invalid`）として記録します（特殊な文字は 1 文字ずつバックスラッシュでエスケープします）。
- 実行の値はグループ名ごとにまとめ、最初に出た順（コマンドの順、正規表現の順、一致の順）に 1 行ずつにします。同じ名前の複数の値はセットのつなぎ方（カンマまたは改行）で連結します。正規表現なしで使ったコンソール出力は名前の無い行になります。
- 行数の上限はそのコマンドが加える部分に効き、値の中の改行も数えます。超えた分は捨てて、切り詰めたことを示します。同じ文字列を何度も取り込む正規表現でも報告が大きくなりすぎないよう、値の大きさにも上限があり、1 つのコマンドの値と 1 つの実行の表示用の値はそれぞれ 1 MiB まで（定数 `MaxCommandValueBytes`、`MaxDisplayValueBytes`）です。超えた分は文字の途中で切らずに捨て、同じく切り詰めたことを示します。
- 値はコマンドの終了時に、エージェントが実行した定義の正規表現で取り出して報告します。セントラルは計算し直さないので、後で正規表現を変えても過去の結果は変わりません。コマンドごとの値（名前と値の組）と実行ごとの行を構造のまま保存します。
- 不正な UTF-8 は、保存ではバイトのまま残し、表示と正規表現の照合のときだけ置換文字にします。

#### 12.5.7 コンソール出力

- 1 つのコマンドにつき 1 MiB まで保存します。超えた分は読んで捨て、全体の大きさと切り詰めたことを記録します。
- 報告は検知と同じ未送信の報告の仕組みで送ります（大きさの上限は 12.5.2 の「報告」）。

#### 12.5.8 セントラルでの保存と保存期間

- 報告は冪等に保存します（実行は `run_uid`、コマンドの結果は実行と位置ごとに 1 回、実行を閉じるのは最初の終了の報告だけ。規則は [API仕様.md](API仕様.md) の 14 章）。監視対象の DB に無いセットの実行は捨てます。
- 1 時間ごとの保存期間の処理で、受け取った日時が `retention_days` より古い実行を（各セットの最後の 1 件も含めて）削除し、セットごとに保存する回数を超えた終わった実行を古い順に削除し、終わった指示（実行済み、期限切れ、破棄）を `retention_days` で削除します。
- コマンドセットの結果について、メールで通知することはありません。

#### 12.5.9 権限と閲覧者が受け取るもの

- 管理者は、定義の一覧、表示、作成、変更、削除、インポート、実行の指示と破棄、すべての結果の画面を使えます。CLI（`ctl`）はすべての操作ができ、再認証を求められません。
- 閲覧者は結果の画面（最新の結果、実行の履歴、実行の詳細）だけを使えます。閲覧者が受け取るのは、セット名、表示用の値、結果の区分、日時と、コマンドごとの戻り値、結果の区分、コンソール出力です（実行の詳細では実行しなかったコマンドの数も受け取ります）。コマンドライン、備考、OS のユーザー、作業ディレクトリ、スケジュール、用途、説明、正規表現、戻り値の指定、コマンドごとに取り出した値、実行の始まり方（手動か定期か、定期の予定時刻、実行指示の ID）、セットのコマンドの数は受け取りません（応答の項目は [API仕様.md](API仕様.md) の 4.1 章）。定義の画面と部品は管理者用の部分で、閲覧者のブラウザには転送しません（13.1.1）。

#### 12.5.10 変更のための再認証

- ブラウザからコマンドセットを作成、変更、削除、インポートするには、そのログインセッションで 1 時間以内に、メールで届いた再認証のコードを入力している必要があります。満たさない要求は `428` で拒否し、何も変更しません。画面はコードを求め、入力の後に同じ操作をやり直します（要求と応答は [API仕様.md](API仕様.md) の 2 章）。
- ログインのときに入力したコードは数えません。信頼済み、確認済みのブラウザでも省きません。「信頼する」の選択肢はありません。実行の指示と破棄、検証、閲覧は対象外です。CLI は対象外です。開発モード（`smtp.host` が空）では求めません。
- コードはアカウントのメールアドレスへ、要求の中で同期して送ります（用途は `re-authentication for changes to command sets`）。条件はログインのコードと同じで、6 桁の数字、有効期限 10 分、誤りは 5 回まで、保存はサーバーの鍵による HMAC（目的、アカウント、セッションに結び付ける）だけです。正しいコードは 1 つの SQL 文で使用済みにするので、1 つのコードで成功するのは 1 回だけです。コードはそれを求めたセッションでしか入力できず、同じセッションの新しい要求は前のコードを置き換えます。
- 誤ったコードは `400` で返し（`401` はブラウザがログアウトとして扱うため）、ログインの失敗の回数には数えません。5 回誤ると、または期限を過ぎると、コードを破棄して `410` を返します。メールを送れない場合は `503` で、履歴（`account`）に `step_up_code_failed` を残し、コードを作りません。
- 正しいコードを入力すると、そのセッションに時刻（`sessions.step_up_at`）を記録します。有効なのはその時刻から 1 時間（定数 `StepUpValidity`。使っても延びない）で、そのセッションだけです。同じアカウントの別のセッションには効きません。パスワードやメールアドレスの変更、無効化では、残すセッションも含めて記録を消します（`modules.RevokeAccountAuth`。12.4 の表の「セッション」で消えるもの以外も対象）。ログアウトでセッションごと消えます。

#### 12.5.11 履歴

- 分類 `command` に、セットの作成（`created`）、変更（`updated`）、削除（`deleted`）、インポート（`imported`）、実行の指示（`run_requested`）、指示の破棄（`request_discarded`）、指示の期限切れ（`request_expired`。操作者は `system`）を記録します。対象は「<監視対象名> / <セット名>」です。
- 閲覧者には分類 `command` の履歴を返しません（[API仕様.md](API仕様.md) の 11 章）。再認証のコードを送れなかったことは分類 `account` に記録します。

## 13. フロントエンド

### 13.1 構成

- Vite + React 19 + TypeScript + Tailwind CSS v4（`@tailwindcss/vite`）+ react-router-dom + i18next。
- `yarn build` の出力 `frontend/dist` を Go バイナリに埋め込み、ブラウザ用の待ち受けで配信します。
- API の呼び出しは `src/api/client.ts`、型は `src/types.ts` にまとめています。401 を受けるとログイン画面に移り、ログイン後に元の画面に戻ります。
- ログイン中のアカウントは `src/context/AuthContext.tsx` で共有します。判定はすべてサーバーでも行います。

### 13.1.1 管理者用の部分の配信

管理者だけが使うもの（画面、閲覧できる画面の中の操作の部品、ナビの項目、文言、API の呼び出し）は、閲覧者のブラウザには転送しません。ログイン前のブラウザにも転送しません。

- フロントエンドのビルドには 2 つのエントリがあります。`main`（`index.html`。全員がダウンロードする）と `admin`（`src/admin/entry.tsx`。管理者用）です。管理者用のものはすべて `src/admin/` に置きます（ページ、部品 `parts/`、API の関数 `api.ts`、文言 `i18n/en.json` と `ja.json`）。
- main には汎用の拡張の仕組みだけがあります。`src/extensions/registry.ts` の `registerExtension` で、拡張がルート、ナビの項目、名前の付いた差し込み口（`src/components/Slot.tsx` の `<Slot>`）に入れる部品、文言を登録します。main は、管理者用の画面のパス、API のパス、文言のキー、アイコンの名前を含みません。差し込み口の名前と、それに渡す props の名前も、管理者の機能を名指ししない一般的な名前にします（例: テンプレートの編集部品を入れる口は `templateDetail.panel` で、開いている間はページの内容の代わりに表示されます）。
- 読み込み: main は `/auth/me` の後（とログインの後）に `GET /ui/modules` を呼び、返った URL を動的な `import()` で読み込んでから画面を表示します（`src/extensions/loader.ts`）。閲覧者には空の一覧が返るので、何も読み込みません。読み込んだ後にセッションが終わると（ログアウト、401）、読み込んだ部品を外せないため、`/login` へページ全体を読み込み直します。開発用のサーバー（`yarn dev`）では、管理者なら `src/admin/entry.tsx` を直接読み込みます。
- 配信: セントラルは起動時に、埋め込んだビルドのマニフェスト（`.vite/manifest.json`）から、admin のエントリから（`imports`、`dynamicImports`、`css`、`assets` をたどって）使うファイルのうち、`index.html` から使うファイルを除いたものを求めます。これらのファイルは、有効な管理者のセッションの Cookie がある要求にだけ、`Cache-Control: private, no-store` を付けて返します。それ以外の要求（未ログイン、閲覧者）には、存在しないパスと同じ応答（`index.html`）を返します。`.vite/` の下は誰にも返しません（存在しないパスと同じ）。この判定はセッションの検証（API と同じ関数）を使いますが、セッションの期限は延ばしません。マニフェストが無い、または admin のエントリが無いビルドでは、何も制限せず、`GET /ui/modules` は空の一覧を返します（起動時にログに 1 回出力します）。
- 閲覧者が管理者用の画面の URL を開くと、ルートが登録されていないので、存在しない URL と同じ「見つからない」画面になります。管理者用の API への閲覧者の要求も、存在しないパスと同じ応答になります（[API仕様.md](API仕様.md) の 1.3）。セントラルはブラウザ用の API のルートを 2 つの表（管理者用はすべてのルート、閲覧者用は全員が使えるルートだけ）に登録し、セッションの権限でどちらかに渡します。

### 13.2 テーマと多言語対応

- 色は `frontend/tailwind.config.js` のセマンティックトークン（`canvas`、`surface`、`ink`、`muted`、`line`、`accent`、`danger`、`warning`、`success` とその soft / hover）を `light-dark()` で定義し、OS の設定に従ってライト / ダークを切り替えます。
- 対応言語は英語と日本語（`src/i18n/en.json` / `ja.json`）です。表示言語はアカウントごとの設定で、値は [API仕様.md](API仕様.md) の 2 章（`Me`）のとおりです。自動選択はブラウザの言語設定（`navigator.languages`）から判別します。
- アカウントの作成時に指定します（省略した場合は [API仕様.md](API仕様.md) の「アカウント」のとおり）。ブラウザ画面での作成の初期値は `auto` です。
- 言語の設定はアカウントのテーブル（`accounts`）にだけ保存し、ブラウザには保存しません。ログイン後はそのアカウントの設定で表示し、ヘッダーの言語の切り替えはログイン中のアカウントの設定を変更します（`PUT /auth/language`）。ログイン画面はブラウザの言語から判別して表示し、そこでの切り替えはその画面の表示だけに使います。
- サーバーが画面に送る文（エラー、検証の問題、適用の結果、履歴など）は、英文のフィールドの隣にコードとパラメーターで表したメッセージ（`<フィールド>_i18n`。形は [API仕様.md](API仕様.md) の 1.2）を付けて返し、画面はコードで表示の言語の文にします。英文は以前と同じで、CLI とログは英文だけを使います（CLI の人向けの表示は `*_i18n` を出さず、`--json` は応答をそのまま出します）。
  - コードと英語のひな形は `app/modules/i18nmsg_catalog.go`（型 `Msg` と `Problem` は `i18nmsg.go`）に 1 回だけ書き、画面の文言は `srv.<コード>` に置きます。管理者だけが受け取るコードは `src/admin/i18n`、それ以外は `src/i18n` に置きます。`go test` の `TestMessageCatalog` が、英文が Go と `en.json` で同じこと、置き場所が受け取る人に合うこと、`ja.json` に同じキーと置き換えの名前があることを確かめます。コードを足すときは、この 3 か所（Go の一覧、`en.json`、`ja.json`）に足します。
  - 画面は `src/utils/serverText.ts` の `serverText` / `problemText` で文にします。コードが空なら文をそのまま、メッセージの一部（入れ子を含む）のコードがその言語の文言に無ければ、全体を英文で表示します。混雑（`common.busy`、またはコードの無い 503）と内部エラー（`common.internal_error`、またはコードの無い 500）は、画面の既存の文言（混雑、エラー）で表示します。
- サーバーが保存して後で画面に出す文のうち、適用の結果（8.2）、内蔵エージェントの停止の理由（`GET /overview` の `message_i18n`。メモリーだけに持つ）、監視ルールの版 1 のコメント（`rule_versions.comment_i18n`。人が書いたコメントは対象外）、組み込みテンプレートの説明（コード `template.builtin.<名前>`）は、英文と同じ内容のメッセージを API で返し、画面は表示の言語で表示します。履歴の対象と詳細も同じで、記録するときに英文（`history.target` と `history.detail`）とメッセージ（`history.i18n`）を同時に記録し（`core.history`、CLI の `central init-admin`、`central reset-password`、`central config set` / `unset`）、`GET /history` とエージェントの詳細の `token_history` で `target_i18n` と `detail_i18n` を返します。英語にすると記録した英文と一致するものだけを返します。
- CLI、エージェントとセントラルのログ、通知メールは英語だけを使い、ロケールが `C`（`LANG=C`）でも動作します。トークン名やルール名など利用者が入力した値は、そのまま表示します。

## 14. 拡張の方法

auditd 以外の監視機能を加える場合は、次の仕組みの上に追加します。

1. `modules.RuleContent` に種類の設定を追加し、検証とテンプレートの展開の規則（`scalarFields` または一覧の結合）を追加する。
2. `modules.DetectionTypes` に種類を追加し、`AgentRuntime.Cycle` の中で検知を収集して、`DetectionReport` として報告に加える。
3. 必要に応じて、セントラルで同じ検知とみなす条件（`workers` の `detectionFingerprint`。種類によって判定に使う項目が異なる）を追加する。画面は種類を固定で持つため、種類の一覧（`src/types.ts`、`src/utils/ruleContent.ts`）、表示名（`src/i18n`）、監視ルールの編集と表示の節を追加する。
4. トークン、適用、報告、検知の保存、抑止条件、通知、アカウントの仕組みはそのまま使える。

## 15. ビルド、テスト、リリース

- Go は 1.27.4、フロントエンドのパッケージ管理は yarn 4.18.1（`packageManager`）を使います。npm は使いません。

- `make lint`: `go vet`、`staticcheck`、`golangci-lint`（`.golangci.yml`）、`yarn lint` を実行します。
- `make test`: `go test ./...`。セントラルの API（認証、権限と閲覧者への管理者用のルートの隠し方、管理者用のファイルの配信、トークンの更新と再発行、インスタンス ID、検知の集約、抑止、通知、コマンドセットの同期と報告と保存期間とインポートと閲覧者への応答、再認証）とモジュール（マージ、検証、パスの判定、auditd の記録の解析、走査、未送信の保存、コマンドセットの検証、スケジュール、値の取り出し、実行（実際の bash）、CLI の引数）のテストがあります。
- フロントエンドのビルド（`yarn build`、Vite）は、`main`（`index.html`）と `admin`（`src/admin/entry.tsx`）の 2 つのエントリから、ファイル名が内容のハッシュだけのファイル（`assets/[hash].js`、`assets/[hash][extname]`）と、マニフェスト `frontend/dist/.vite/manifest.json` を出力します。`embed.go` は `all:frontend/dist` を埋め込むので、マニフェストも埋め込まれます。セントラルはマニフェストを配信の判定にだけ使い、配信しません（13.1.1）。
- `make`（`make build`）: フロントエンドをビルドし、Linux（amd64 / arm64）向けにビルドして `bin/` に出力します。Linux 固有のシステムコールを使うため、他の OS 向けにはビルドしません。
- `make pack`: `bin/` のバイナリを、アーキテクチャごとに `release/mimamori_<VERSION>_linux_<arch>.zip`（中のファイル名は `mimamori`）にまとめます。先に `make` でビルドしておきます。
- `make format`: `go fmt` とフロントエンドの `yarn format` で整形します。
- `make clean`: `bin/`、`release/`、`frontend/dist` を削除します。
- バージョンは `Makefile` の `VERSION` を `-ldflags "-X main.version=..."` で埋め込みます。
